Rule analysis

Flags string literals containing curly-brace expressions without an 'f' prefix when they appear to be intended as f-strings.

Fix: Adds an 'f' prefix to the string literal, converting it into an f-string so that expressions within curly braces are evaluated.

12 hazards
  • The string may be used in a context expecting a literal string with braces (e.g., regex, SQL, or templating), where adding 'f' would cause runtime errors due to undefined variable names or syntax issues.
  • If the string contains backslashes, the f-string prefix changes how escape sequences are interpreted (e.g., '\n' vs. actual newline), potentially altering the string value.
  • Comments placed inside the string literal (e.g., via concatenation or multi-line strings) may be misinterpreted as code or removed during parsing after the fix.
  • In triple-quoted strings, adding 'f' may interfere with indentation processing if the string relies on dedent behavior that differs between raw and f-string handling.
  • If the string is part of a larger expression (e.g., concatenation with other strings or variables), the fix may break operator precedence or introduce unintended grouping.
  • When the string appears in a dictionary key or set literal, the rewritten f-string may raise a TypeError at runtime if the expression evaluates to an unhashable type.
  • If the string is used in a byte string context (e.g., b"{x}"), the fix is invalid and would produce a SyntaxError, though Ruff should avoid suggesting it in such cases.
  • The fix may inadvertently capture variables from an outer scope that were not intended to be used, especially in nested functions or comprehensions, changing closure behavior.
  • In f-strings, expressions are evaluated left-to-right; if the original string relied on brace literals for formatting (e.g., in a loop generating templates), evaluation order side effects could emerge.
  • If the string contains a '#' inside braces (e.g., "{x#comment}"), the f-string parser may interpret it as a comment, truncating the expression and causing a SyntaxError or incorrect evaluation.
  • When the string is passed to a function like gettext or logging that expects a format string with named placeholders, the f-string will evaluate the expressions immediately, bypassing the intended deferred formatting mechanism.
  • If the string is defined but never used (dead code), the fix still applies and may introduce unnecessary runtime overhead or NameErrors if variables are undefined.
