Rule analysis

Flags JSX elements without children that have explicit closing tags.

Fix: Replaces the explicit opening and closing tags with a single self-closing tag, preserving all attributes, whitespace between '<' and tag name, and whitespace between tag name and '>' if present; removes the entire closing tag including its preceding whitespace.

10 hazards
  • Rewriting <>...</> changes the semantics because React.Fragment without a key cannot be expressed as a self-closing fragment, so the fix would drop the implicit key prop and potentially break reconciliation when used in lists.
  • If the closing tag contains a comment (e.g., </div><!-- note -->), removing it deletes that comment, altering the source file’s comment structure.
  • When ignoreHtmlElements is true, the rule does not fire on HTML elements, but if mistakenly applied, rewriting <div></div> to <div /> could be treated differently by the browser in rare cases involving custom elements or formatting-sensitive contexts.
  • If the opening tag has a spread attribute like <div {...props}></div>, the fix preserves it, but if the spread evaluates to an object containing a children property, removing the closing tag could cause the element to receive an unexpected children prop, altering behavior.
  • If the element is a custom component that relies on receiving children via props.children even when empty (e.g., for layout measurements), changing to self-closing may cause it to receive undefined instead of an empty array, breaking logic that checks Array.isArray(props.children).
  • If the JSX is inside a type assertion or embedded in a larger expression where the parser expects a closing tag to delimit the JSX scope, removing it could cause the parser to consume too many tokens, resulting in a syntax error.
  • If the closing tag is on a separate line and preceded by a line comment (e.g., <div></div> // note ), the fix’s removal of the newline before the closing tag could bring the comment onto the previous line, potentially changing its association or causing trailing whitespace issues.
  • If the element uses a namespace prefix like <svg:circle></svg:circle>, rewriting to <svg:circle /> is valid, but some older JSX transformers might not recognize self-closing namespaced tags, leading to a parse error.
  • If the opening tag contains a JSX expression attribute like <div data-value={getValue()}></div> and getValue() has side effects, the fix does not change evaluation order, but if the closing tag were mistakenly thought to delay execution, removing it could be incorrectly assumed to affect timing—though in reality, no such delay exists.
  • If the file is being processed by a tool that relies on the presence of closing tags to match regions for folding or refactoring, removing them could break those tool’s region detection.
