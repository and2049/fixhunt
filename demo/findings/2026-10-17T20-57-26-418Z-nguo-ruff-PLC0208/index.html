Rule analysis

The rule flags iteration over set literals containing only literal elements.

Fix: Replace the set literal with a tuple literal containing the same elements in arbitrary order, preserving all literal values exactly as written.

10 hazards
  • Rewriting a set literal used elsewhere in the same scope changes behavior if the original set was referenced by variable or attribute after the loop, as the tuple replacement is not equivalent for membership tests or mutation.
  • If the set literal appears in a context where its unhashable nature is relied upon (e.g., passed to a function expecting a set), replacing it with a tuple may cause TypeError or logic errors due to type mismatch.
  • When the set literal is part of a larger expression (e.g., union or intersection with another set), replacing it with a tuple breaks the operation as tuples do not support set methods.
  • If the loop variable is mutated within the loop body and later used to reconstruct a set, the original iteration order (arbitrary but consistent per run) may affect downstream logic differently than tuple order.
  • In rare cases where the set literal's hash randomization affects iteration order across runs, replacing it with a fixed-order tuple may make behavior deterministic where it was previously nondeterministic, altering probabilistic outcomes.
  • If the set literal contains duplicate literals (e.g., {1, 1, 2}), the set deduplicates them, but the tuple rewrite preserves duplicates, changing the number of iterations and potentially breaking logic relying on unique iteration.
  • Comments attached to the set literal (e.g., {1, 2 # inline}) may be lost or misplaced during the rewrite, as the autofix typically does not preserve comment placement within the literal.
  • If the set literal is defined on a line with a trailing comma (e.g., {1, 2,}), the autofix may incorrectly omit or mishandle the comma when generating the tuple, leading to a syntax error or unintended single-element tuple.
  • When the set literal is used in a default argument or class attribute, replacing it with a tuple may cause shared mutable state issues if the tuple is mistakenly treated as mutable, though tuples are immutable—this hazard is low but included for completeness regarding developer assumption.
  • In code that relies on the set literal being evaluated as a new object each time (e.g., in a loop or function call), the tuple rewrite also creates a new object each time, so no behavioral change occurs from object identity alone, but any reliance on set-specific identity (e.g., 'is' checks against a known set) would fail.
