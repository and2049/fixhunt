Rule analysis

Flags unnecessary 'u' prefixes on string literals since all strings are Unicode in Python 3.

Fix: Removes the 'u' prefix from string literals, leaving the literal unchanged otherwise.

10 hazards
  • Rewriting ur"..." to r"..." removes the Unicode guarantee, potentially altering behavior if non-ASCII characters rely on implicit decoding in Python 2 contexts (though irrelevant in pure Python 3).
  • Rewriting u"..." to "..." may expose reliance on the 'u' prefix for disambiguation in code generation or eval contexts where the prefix is inspected as source.
  • If the 'u' prefix is part of a larger token due to missing whitespace (e.g., u"x"+y), removing it could change tokenization and break parsing.
  • In bytestring concatenation like u"a" + b"b", removing 'u' does not affect type but could mislead readers about intent, though behavior remains identical.
  • The fix does not adjust surrounding whitespace or formatting, so comments attached via line continuations or inline may become misaligned if the prefix removal alters visual indentation in multi-line edits.
  • In f-strings like uf"{expr}", removing 'u' yields f"{expr}", which is equivalent in Python 3, but if the code is processed by a tool that expects the 'u' prefix for Unicode enforcement, downstream tooling may behave differently.
  • When used in annotations or stringized expressions (e.g., typing annotations), the 'u' prefix has no semantic value, but its removal could affect tools that parse source for metadata.
  • If the string literal is part of a macro or preprocessor-like scheme (e.g., via custom imports or exec), removing 'u' could alter the seen source and break expected transformations.
  • In rare cases involving the tokenizer API or ast.unparse, preserving the exact source form may be required for round-trip fidelity, and removing 'u' breaks that.
  • The rewrite assumes the literal is a string; if mistakenly applied to non-string contexts due to buggy detection, it would corrupt syntax.
