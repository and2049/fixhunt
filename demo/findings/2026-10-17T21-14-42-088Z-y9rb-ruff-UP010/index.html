Rule analysis

Flags any imported name from `__future__` when the target Python version already includes that feature by default.

Fix: Removes the entire `from __future__ import ...` statement, leaving surrounding code and whitespace unchanged except for the deletion of that line.

12 hazards
  • Deleting a trailing comment on the same line as the import removes that comment, altering source documentation.
  • If the `__future__` import is the only thing keeping a module-level variable alive (e.g., via side effect), removing it may change initialization behavior.
  • In rare cases where a future import suppresses a SyntaxWarning (e.g., bare `except:`), removal could resurface the warning.
  • If the import is inside a conditional block that never executes, removing it changes the module's abstract syntax tree but not runtime behavior—still, tools relying on static structure may be affected.
  • When the import is followed by a blank line that is part of a docstring or block comment grouping, deleting the import line may visually merge sections, misleading readers.
  • If a linter or tool expects the `__future__` import to be present to determine feature availability (e.g., for type checking), removing it may cause false positives.
  • In Python 2.x environments where the feature is not actually available, removing the import would cause a runtime error—but the rule assumes target-version >= feature availability.
  • If the import line contains a line continuation (`\`) that also serves another purpose (e.g., in a multi-statement line), removing it could cause a syntax error.
  • When the import is used to suppress a future-warning in development mode, removing it may re-enable noisy warnings during execution.
  • If the module relies on the import to affect the behavior of `eval` or `exec` calls within the same module, removing it changes how those functions interpret code.
  • In notebooks or interactive environments where `__future__` imports affect cell semantics, removal may alter execution across cells.
  • If the import is aliased (e.g., `from __future__ import annotations as ann`), the rule does not fire, but if it did, removing it would break the alias—however, the rule correctly does not flag aliased imports.
