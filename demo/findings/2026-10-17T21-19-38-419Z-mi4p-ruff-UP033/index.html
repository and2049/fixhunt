Rule analysis

Flags usage of functools.lru_cache with maxsize=None, suggesting replacement with functools.cache.

Fix: Replace 'functools.lru_cache(maxsize=None)' with 'functools.cache' while preserving all other decorators, arguments (like typed), whitespace, and syntactic context.

12 hazards
  • Rewriting inside a lambda or comprehension may alter evaluation timing if the decorator is applied dynamically.
  • If 'functools' is imported as an alias (e.g., import functools as ft), the fix may not apply or may produce invalid syntax.
  • When lru_cache is used via getattr or dynamic attribute access (e.g., getattr(functools, 'lru_cache')), the fix cannot be applied and may be missed.
  • If the call to lru_cache includes unpacked kwargs (**kw) where kw might contain 'maxsize', the fix could incorrectly assume maxsize=None is intended.
  • If maxsize=None is passed as a variable (e.g., maxsize=None_var), the fix would incorrectly trigger and replace with cache, changing behavior.
  • In nested decorator expressions like @functools.lru_cache(maxsize=None)(other_arg), the structure may be misinterpreted during rewrite.
  • Comments attached to the lru_cache call (e.g., # type: ignore) may be lost during the rewrite if not carefully preserved.
  • If functools.cache is not available (Python <3.9), the fix would result in a NameError unless the target-version option allows it.
  • When lru_cache is reassigned to a variable and used conditionally, replacing the attribute access may break if the variable is later rebound.
  • If the module defines a local name 'cache' in the same scope, using functools.cache could be shadowed or misinterpreted after rewrite.
  • In string annotations or forward references (e.g., annotations = {'f': 'functools.lru_cache(maxsize=None)'}), the fix should not apply but might be incorrectly triggered.
  • If the decorator is part of a macro or code-generation scheme (e.g., via exec or eval), the static rewrite does not reflect runtime behavior.
