Rule analysis

Flags unnecessary list() or reversed() wrappers around sorted() calls.

Fix: Replaces list(sorted(...)) with sorted(...) and reversed(sorted(...)) with sorted(..., reverse=True).

8 hazards
  • For reversed(sorted(...)), the fix changes behavior when a custom key function is used because reversed() reverses the final list while sorted(..., reverse=True) performs a reverse sort that may reorder equal elements differently.
  • If the sorted call uses a custom comparator via functools.cmp_to_key, reversed() and reverse=True are not equivalent due to differing stability properties.
  • When the iterable passed to sorted is not a list (e.g., a generator), removing list() in list(sorted(...)) changes the return type from list to an iterator, breaking code that expects a list.
  • If the result of list(sorted(...)) is assigned to a variable and later mutated, the fix may affect aliasing if other references expect a list but now get an iterator.
  • Comments inside the list() or reversed() call (e.g., list(sorted(# comment x))) would be dropped by the rewrite as they are not preserved in the simplified expression.
  • If sorted() is called with side-effecting key or reverse expressions (e.g., sorted(x, key=print(len(i)))), the evaluation order of those expressions is unchanged, but the outer call removal could affect debugging or profiling tools that count function invocations.
  • In rare cases where sorted returns a subclass of list (e.g., from a user-defined class overriding __sorted__), removing list() could change the exact type returned, affecting isinstance checks.
  • If the code relies on the fact that list(sorted(...)) creates a new list object (which it does), and sorted(...) also creates a new list, there is no behavioral difference—but if sorted were overridden to return a singleton or cached result, the fix could expose that, though sorted is built-in and not overridable in standard Python.

Findings

r2-p006 fix-changes-behaviorlabelled safejudge: real · medium singleton_sorted_return_exposure

The fix removes a `list()` call around `sorted()`, which is documented as safe because `sorted()` already returns a list. However, the program monkey-patches `builtins.sorted` to return a cached list instance, so `list(sorted(x))` creates a new list while `sorted(x)` returns the cached instance, changing the identity check `a is b` from `False` to `True`.

Minimized program (13→12 lines)

import builtins
original_sorted = builtins.sorted
cache = []
def cached_sorted(*args, **kwargs):
    if not cache:
        cache.append(original_sorted(*args, **kwargs))
    return cache[0]
builtins.sorted = cached_sorted
x = [3, 1, 2]
a = list(sorted(x))
b = sorted(x)
print(a is b)
