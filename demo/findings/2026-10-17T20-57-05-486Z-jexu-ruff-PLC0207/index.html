Rule analysis

The rule flags str.split() or str.rsplit() calls used immediately after indexing [0] or [-1] when no maxsplit=1 argument is present.

Fix: Adds maxsplit=1 as a keyword argument to the split or rsplit call; if positional arguments exist, inserts maxsplit=1 as the second positional argument after the separator (or as the first if no separator is given).

10 hazards
  • If the call uses *args, inserting maxsplit=1 may cause a duplicate keyword argument error when *args unpacks a value for maxsplit.
  • If the call uses **kwargs, inserting maxsplit=1 may cause a duplicate keyword argument error if **kwargs already contains maxsplit.
  • If the separator argument is a variable that evaluates to None, adding maxsplit=1 as a second positional argument changes the call from split(None) to split(None, 1), which alters behavior (split(None) splits on whitespace, split(None, 1) splits on whitespace at most once).
  • If the call has no separator and uses split(), adding maxsplit=1 as a positional argument changes split() to split(None, 1), altering behavior from splitting on whitespace to splitting on whitespace at most once.
  • If the call uses split('') with an empty separator, adding maxsplit=1 is invalid and raises ValueError because empty separators are not allowed, though the original call would have already raised this error—however, the fix may change the error context or timing if the call was guarded.
  • If the call is part of a larger expression where the split result is used elsewhere (e.g., assigned to a variable then indexed), the fix only applies to the indexed use and may miss optimizing other uses, but this is not a behavioral change—however, the rule only triggers on direct indexing, so indirect uses are not fired on.
  • If the call appears in a lambda or comprehension and the fix introduces a keyword argument that conflicts with a parameter name in the surrounding scope, it could cause a binding conflict (e.g., split(maxsplit=1) where maxsplit is a lambda parameter).
  • If the call is inside a try-except block and the fix changes the exception type (e.g., from TypeError due to duplicate keyword to ValueError), the except handler may not catch it.
  • If the call is commented out or dead code, the fix still applies but may be unnecessary; however, this does not change behavior.
  • If the call uses keyword arguments for sep or maxsplit already, the fix may incorrectly insert a duplicate (though the rule avoids this by checking for existing maxsplit).
