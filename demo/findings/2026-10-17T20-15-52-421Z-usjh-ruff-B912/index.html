Rule analysis

Flags map() calls lacking an explicit 'strict' keyword argument when invoked with multiple iterables or starred arguments.

Fix: Adds ', strict=True' as the final keyword argument to the map call, preserving all existing arguments and their order.

12 hazards
  • If the original call already contains a '**kwargs' unpacking that might include 'strict', adding another 'strict' argument creates a duplicate keyword error.
  • If the map call is part of a larger expression where trailing commas affect parsing (e.g., inside a tuple literal), inserting ', strict=True' could alter grouping or create invalid syntax.
  • When the map call appears in a context where the argument list ends with a bare '*args' (no following comma), inserting ', strict=True' after it may be misinterpreted as part of the starred expression rather than a keyword argument.
  • If the function being mapped relies on side effects that occur during iteration, changing from implicit truncation to strict length checking could cause early termination via ValueError where previously the loop would have completed silently.
  • In code targeting Python versions <3.14, the added 'strict' argument will raise a TypeError at runtime since older map implementations do not accept this parameter.
  • If the map call is embedded within a lambda or comprehension where the argument list is constructed dynamically, the static insertion of 'strict=True' may not reflect the intended runtime behavior.
  • Comments placed between the last positional argument and the closing parenthesis (e.g., 'map(f, a, b # comment)') risk being displaced or rendered invalid when the fix inserts ', strict=True' before the closing parenthesis.
  • When the map call uses positional-only parameters or appears in a stub file (.pyi), inserting 'strict=True' may violate type checker expectations or overload definitions.
  • If the iterables passed to map are actually the same object (e.g., map(f, x, x)), the strict check passes trivially, but the fix still adds noise without benefit.
  • In code that intentionally relies on zip-like truncation behavior (e.g., processing paired data where excess elements are ignorable), enforcing strict=True introduces unnecessary failures.
  • If the map call is written across multiple lines with inconsistent indentation, the autofix may insert ', strict=True' at an incorrect indentation level, breaking formatting rules.
  • When the map call is immediately followed by a method chain (e.g., map(f, a, b).filter(...)), inserting ', strict=True' before the closing parenthesis does not affect the chain, but if the chain starts on the same line, whitespace handling could become ambiguous.
