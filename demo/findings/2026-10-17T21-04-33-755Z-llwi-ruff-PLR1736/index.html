Rule analysis

Flags redundant indexing of a list when using enumerate where the element is already provided by the loop variables.

Fix: Replace the indexed list access with the loop variable that corresponds to the current element from enumerate.

10 hazards
  • Rewriting `lst[i]` to `x` changes behavior if `lst` is reassigned within the loop body, as the original code uses the updated list while the fix uses the stale loop variable.
  • If `lst` is a property with a setter, accessing `lst[i]` may trigger the setter on each iteration, whereas using `x` avoids this entirely.
  • When `lst` is a mutable local variable that is later rebound in an outer scope, the fix captures the value at loop entry, while the original reflects rebinds.
  • If the list element is a class instance with a custom `__getitem__` that has side effects, replacing `lst[i]` with `x` omits those side effects.
  • In cases where `lst` is a multidimensional list and the index is a tuple (e.g., `lst[i][j]`), the fix cannot be applied because the loop variables do not match the indexing structure.
  • If the loop variable is named identically to the list (e.g., `for lst, lst in enumerate(lst): lst[lst]`), the fix risks incorrect variable capture due to name shadowing.
  • When the indexed access appears in an annotated assignment (e.g., `lst[i]: int = 5`), removing the index breaks the annotation's target.
  • If the indexed expression is part of a larger subscript (e.g., `lst[i][0]`), the fix would incorrectly replace only the outer index, leaving an invalid access.
  • Comments attached to the indexed expression (e.g., `lst[i] # comment`) may be lost if the autofix does not preserve trailing comments during replacement.
  • In a `walrus` expression like `if (tmp := lst[i]) > 0:`, replacing `lst[i]` with `x` alters the assignment target and may affect subsequent uses of `tmp`.
