Rule analysis

The rule flags direct comparison of an object's type to the type of None using 'type(x) is type(None)' patterns.

Fix: Replace 'type(X) is type(None)' with 'X is None', 'type(X) == type(None)' with 'X is None', 'type(X) is not type(None)' with 'X is not None', and 'type(X) != type(None)' with 'X is not None'.

10 hazards
  • Rewriting 'type(obj) is type(None)' when 'obj' is a property with side effects changes evaluation timing and may execute getter twice.
  • If 'obj' is a function call like 'type(func()) is type(None)', the fix 'func() is None' alters side effects by calling func() once instead of evaluating its return type.
  • In default arguments like 'def f(x=type(obj) is type(None)):', moving the expression changes when 'obj' is evaluated relative to function definition.
  • When used in annotations like 'List[type(obj) is type(None)]', the fix breaks syntax as 'obj is None' is not a valid type annotation.
  • If 'obj' is a class attribute accessed via 'type(cls.attr) is type(None)', the fix may trigger __getattribute__ differently under metaclasses.
  • In comprehensions with filtering like '[x for x in ys if type(x) is type(None)]', the fix preserves behavior but may affect performance characteristics in tight loops.
  • When 'obj' is a variable named 'None' in local scope, 'type(None) is type(None)' becomes ambiguous after fix to 'None is None' due to shadowing.
  • If the comparison is part of a larger expression like 'type(a) is type(None) and b', fixing only part may create invalid syntax or alter precedence.
  • In try/except blocks where 'obj' evaluation raises exceptions, the fix changes whether the exception occurs during type checking or identity check.
  • When comments are attached to the 'type' expression like 'type(x) # check is type(None)', the fix may detach or lose the comment during AST rewrite.
