Rule analysis

Flags backslash-character combinations in string literals that do not form valid Python escape sequences.

Fix: Replace the invalid escape sequence by doubling the backslash before the character to treat it as a literal backslash followed by that character, preserving all other string content and quote style.

12 hazards
  • In raw strings (r"..."), doubling backslashes introduces extra literal backslashes, altering the intended pattern (e.g., r"\." becomes r"\\." which matches two backslashes then a dot).
  • In byte strings, the fix may produce invalid byte escape sequences if the character after the backslash is not a valid hex digit or octal digit, causing a SyntaxError.
  • If the string is part of a larger expression where the backslash was intended as a line continuation (outside string literals), the fix does not apply and is irrelevant, but misidentification could lead to incorrect changes.
  • When the invalid escape appears in a docstring or comment-like context inside a string, doubling the backslash changes the literal text, potentially breaking tools that parse the string content (e.g., help(), doctests).
  • If the string uses triple quotes and the invalid escape spans across implicit line joining due to a backslash at end-of-line inside the string, fixing it may disrupt the line continuation semantics within the string content.
  • In f-strings, if the invalid escape occurs inside an expression part ({...}), the fix is not applied there; but if mistakenly applied, it would corrupt the expression syntax.
  • If the string is adjacent to another string literal for concatenation (e.g., "a" "b"), and the fix is applied only to one part, the resulting concatenated string may have unintended backslash duplication.
  • When the invalid escape is immediately followed by a quote of the same kind that ends the string (e.g., "\""), doubling the backslash may interfere with the string termination if not handled correctly by the lexer during refactoring.
  • If the string contains mixed valid and invalid escapes (e.g., "\n\_"), fixing only the invalid part may create an inconsistent interpretation where the valid escape remains unchanged but the invalid one becomes literal, which may be the intent but must be verified.
  • In code generated by macros or templating systems where backslashes are placeholders, doubling them could break the generator's assumptions about the output format.
  • When the string is used in a regex context via re.sub or similar, doubling backslashes changes the number of escape layers, potentially requiring compensatory changes elsewhere in the pattern.
  • If the invalid escape is part of a Unicode name escape like \N{...} with invalid contents, doubling the backslash yields a literal backslash-N, which is not equivalent and may raise a different error at runtime.
