Rule analysis

Flags Decimal() constructor calls where the argument is a floating-point literal.

Fix: Replace the floating-point literal argument with its exact string representation using repr() to preserve the original float's value.

12 hazards
  • If the float argument is a variable (e.g., Decimal(x)), the fix incorrectly replaces it with a string literal, altering semantics and potentially causing TypeError.
  • If the float argument is an expression (e.g., Decimal(1.0 + 2.0)), the fix replaces the entire expression with a string, changing runtime behavior.
  • If the float is a special value like float('nan') or float('inf'), repr() produces strings like 'nan' or 'inf', which Decimal() accepts but may propagate differently in downstream calculations.
  • If the code relies on the exact binary approximation of the float (e.g., for bit-level reproduction), converting to string then to Decimal yields a different rational number than the original float-to-Decimal conversion.
  • If the Decimal call is inside a larger expression (e.g., Decimal(1.2) + 3), the fix only affects the constructor argument, but surrounding code may still behave differently due to altered precision.
  • If the float literal is part of a tuple or list unpacked via *args (e.g., Decimal(*[1.2])), the fix does not apply and Ruff may not flag it, but if it did, rewriting would break unpacking.
  • If the code uses a custom Decimal subclass that overrides __init__ to expect a float, replacing with a string breaks initialization.
  • If the float literal appears in a comment or docstring near the call (e.g., # value: 1.2), the fix does not touch comments, but the semantic change may invalidate the comment's accuracy.
  • If the float is the result of a function call with side effects (e.g., Decimal(get_price())), the fix would incorrectly replace the call with a string, eliminating side effects.
  • If the code runs under a strict typing regime (e.g., mypy) that expects Decimal(float), the rewritten Decimal(str) may trigger false-positive type errors.
  • If the float literal is syntactically identical to an integer literal but typed as float (e.g., Decimal(2.0)), the fix produces '2.0', which is semantically equivalent but may affect code generation tools that distinguish float vs int origins.
  • If the code is parsed by a tool that relies on the AST node type being a constant float, replacing it with a string constant alters the AST and may break downstream tooling.
