Rule analysis

Flags standalone TypeVar and ParamSpec usage in generic function annotations.

Fix: Removes the standalone TypeVar/ParamSpec variable definitions and adds the corresponding type parameters to the function signature using PEP 695 syntax (e.g., def func[T](x: T) -> T: ...).

12 hazards
  • Rewriting changes the scope of the type variable from module-level to function-local, which can break code that references the variable outside the function (e.g., in other function signatures or class definitions).
  • If the TypeVar uses a 'default' argument (Python 3.13+), the fix omits the default, altering the inferred type when the parameter is omitted.
  • If the TypeVar has a 'bound' constraint, the fix does not preserve the bound in the new syntax, potentially changing type-checking behavior.
  • If the TypeVar is contravariant or covariant, the fix drops the variance keyword, and PEP 695 infers variance instead, which may differ and affect subtyping relationships.
  • If multiple functions share the same TypeVar, rewriting one function leaves the shared variable defined but may cause mismatches if other functions are not also rewritten.
  • If the TypeVar is used in a default argument value (e.g., def f(x: T = SomeDefault)), the fix does not update the default expression, leaving a reference to an undefined name after removal.
  • If the TypeVar is used in a type ignore comment or string annotation nearby, removing the variable definition may cause those references to become unresolved.
  • If the file contains a conditional import or definition of the TypeVar (e.g., inside an if block), the fix may hoist or misplace the removal, causing syntax errors.
  • If the TypeVar is aliased via import (e.g., from mod import TypeVar as TV), the rule may not detect it and leave the alias while incorrectly adding a type parameter, resulting in mixed old/new style.
  • If the function is decorated, the fix inserts type parameters before the decorator, which is invalid syntax.
  • If the function has overlapping type parameters with another generic function in the same scope, the fix may introduce duplicate or conflicting type parameter names.
  • If the code uses a stringized annotation (from __future__ import annotations) and the TypeVar is referenced in a string, removing the definition may break runtime evaluation of annotations.
