Rule analysis

Flags class definitions that explicitly inherit from object, which is redundant in Python 3.

Fix: Removes 'object' from the base class list; if object is the only base, the entire inheritance list is deleted leaving just 'class Name:'; if object is among multiple bases, it is stripped out while preserving order and spacing of remaining bases.

8 hazards
  • Rewriting 'class C(object, Mixin): pass' to 'class C(Mixin): pass' changes the method resolution order (MRO) if Mixin defines methods also present in later bases, altering which method is called via super().
  • If a class uses a metaclass via '__metaclass__' attribute (Python 2) or '__classcell__' in nested scopes, removing 'object' may affect class creation semantics in edge cases involving class cell closure capture.
  • In rare cases where 'object' is used as a placeholder for a dynamically assigned base via metaprogramming (e.g., class decorators that inspect bases), removing it breaks the decorator's assumption about the base list.
  • If the class definition contains a trailing comment after the colon (e.g., 'class Foo(object): # comment'), the autofix may drop the comment when reformatting the line, violating comment preservation safety.
  • When 'object' is the first base and followed by a newline-indented block, removing it may cause the linter/formatter to reindent the block incorrectly if the tool does not preserve whitespace exactly, altering readability though not semantics.
  • In code that relies on the string representation of the class's bases (e.g., for serialization or debugging), removing 'object' changes the output of __bases__, potentially breaking introspection-dependent logic.
  • If a class is defined inside a function and uses 'object' to avoid a name conflict with a local variable named 'object', removing it could cause unintended binding (though this is extremely unlikely and non-standard).
  • When using Python 2 compatibility layers like 'six' or 'future', some code may rely on explicit 'object' inheritance to trigger new-style class behavior; removing it in Py2 would break the code, but the rule only applies in Py3+ contexts—still, if the file is run under Py2 due to misconfiguration, the fix introduces a regression.

Findings

r1-p003 fix-changes-behaviorlabelled safejudge: real · high Method Resolution Order Change

The original class `C(object, Mixin, Base)` is invalid in Python 3 because `object` must not appear alongside other bases in the MRO; the linter's fix removes `object`, which makes the class definition valid and changes the program from crashing with a TypeError to running successfully. This is a silent behavior change in plausible code where the fix alters program correctness, so it should not be considered safe.
