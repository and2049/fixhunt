Rule analysis

Flags redundant constructor calls like str(x), bytes(b), int(n), float(f), bool(v), complex(c) where x is already of the target type.

Fix: Replace the constructor call with its literal equivalent: e.g., str(s) → s when s is a string literal, bytes(b) → b when b is a bytes literal, etc.

12 hazards
  • Rewriting str(expr) to expr changes behavior if expr has side effects (e.g., str(print("x")) vs print("x"))
  • Rewriting bytes(expr) to expr alters evaluation if expr is a function call with side effects
  • Rewriting int(expr) to expr fails if expr is a float (e.g., int(3.9) → 3.9 changes value and type)
  • Rewriting float(expr) to expr breaks if expr is an integer string (e.g., float("4") → "4" raises TypeError in numeric contexts)
  • Rewriting bool(expr) to expr changes truthiness semantics (e.g., bool([]) → [] is falsy but not equivalent in explicit bool checks)
  • Rewriting complex(expr) to expr fails if expr is a real number (e.g., complex(5) → 5 loses imaginary part and changes type)
  • The fix may drop inline comments attached to the constructor call (e.g., str("hi") # comment → "hi" # comment becomes detached or lost)
  • If the constructor name is shadowed locally (e.g., str = lambda x: x; str("a")), the rewrite to "a" ignores the custom behavior
  • In eval or exec contexts, replacing str(...) with its argument may alter namespace resolution if the argument is a variable
  • The rewrite is invalid if the argument is a tuple needing parentheses for disambiguation (e.g., str((1,2)) → (1,2) is fine, but str(1,2) is a syntax error so not fired)
  • If the constructor is used as a callable in higher-order code (e.g., map(str, [...]))
  • Rewriting may interfere with debugging or profiling tools that rely on constructor call sites

r1-p003 fix-changes-behaviorlabelled safejudge: real · medium type_annotation_runtime_eval

The fix rewrote the string literal inside a type annotation from 'int(5)' to '5', changing the value of f.__annotations__['x'] from 'int(5)' to '5'. Type annotations are stored as strings when using from __future__ import annotations or when quoted, and user code (e.g., runtime type checkers, documentation generators) may depend on the exact annotation text. The rule only intends to replace unnecessary constructor calls in executable code, not inside string literals that are not evaluated.
