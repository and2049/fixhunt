Rule analysis

Flags redundant UTF-8 encoding declarations at the top of Python files.

Fix: Removes the UTF-8 encoding declaration line if it is the first or second line (after a shebang) and matches the pattern for UTF-8 (case-insensitive, with or without underscores, and optional spacing).

8 hazards
  • Removing a UTF-8 declaration in a file that actually contains non-UTF-8 encoded bytes would cause a SyntaxError when the file is parsed, as Python would default to UTF-8 decoding.
  • If the file relies on the encoding declaration to specify UTF-8 but is saved in a different encoding (e.g., Latin-1), removing the declaration changes how non-ASCII literals are interpreted, potentially altering string values.
  • The rewrite may remove a comment that is functionally part of a multi-line comment block if the encoding line is mistaken for comment content, though this is unlikely given its specific form.
  • In tools or environments that scan for encoding declarations beyond the first two lines (non-standard), removing it could break those tools even if Python 3+ ignores it.
  • If the encoding line is indented or has leading whitespace (invalid per PEP 263 but sometimes tolerated), the autofix might not trigger, but if it did, removing it could leave meaningless whitespace or affect line-number-sensitive debugging.
  • If the file uses a shebang and the encoding line is the second line, removing it shifts the shebang to line 1 and content to line 2, which is semantically identical but may affect tools that expect the encoding line at a fixed position.
  • In a concatenated script built from multiple files, removing the encoding declaration from a fragment could cause misinterpretation if the fragment is evaluated in isolation before concatenation.
  • If the encoding declaration is duplicated or malformed (e.g., '# coding: utf-8;;'), the autofix may not fire or may partially remove it, leaving syntax errors or strange remnants.

r2-p006 fix-changes-behaviorlabelled safejudge: real · low Non-file context manager relying on line numbers for ID

The fix removes the UTF-8 encoding declaration comment, which shifts all subsequent line numbers up by one. The program uses `inspect.currentframe().f_lineno` to capture and print the current line number, so the observed output changes from 'line 5' to 'line 4'. This is a real behavioral change in a plausible debugging/logging construct that relies on exact line numbers.
