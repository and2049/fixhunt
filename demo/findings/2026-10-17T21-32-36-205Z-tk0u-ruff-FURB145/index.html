Rule analysis

Flags unbounded slice expressions (`seq[:]`) used to copy a sequence when the target is known to be a list.

Fix: Replaces the unbounded slice expression `seq[:]` with the method call `seq.copy()` while preserving the surrounding assignment or expression context.

11 hazards
  • Rewriting `seq[:]` where `seq` is not a list (e.g., a string or tuple) changes the return type from the original sequence type to a list, breaking type expectations.
  • If `seq` is a subclass of list that overrides `__getitem__` but not `copy`, the slice may return a different type than `copy()` produces.
  • When the slice appears in a context relying on the exact object identity of a new list (e.g., `is` checks), `copy()` may produce a different object than slicing in some implementations (though CPython guarantees a new object, this is not language-spec guaranteed).
  • If `seq` is a variable that is deleted or reassigned between the evaluation of the slice and its use in the original code (impossible in a simple expression, but relevant in larger refactorings), the fix does not capture this timing—however, since the fix is applied locally to an expression, this hazard is mitigated; still noted for completeness in complex macro-like scenarios.
  • If the slice expression contains an inline comment (e.g., `a[: # copy]`), the fix may drop or misplace the comment during rewrite, altering source code readability.
  • In code where `seq` is a property with a side-effecting `__getitem__` (highly unconventional but possible), accessing `seq[:]` triggers `__getitem__` once with a slice object, whereas `seq.copy()` may not invoke `__getitem__` at all, changing side-effect timing.
  • If `seq` is a mutable object and the slice is used in a conditional expression where the object might be mutated between evaluation points (not applicable here as the expression is atomic), but note that the fix does not alter evaluation order—it replaces the expression in place.
  • When the slice is part of a larger subscript (e.g., `a[:][0]`), the fix only applies to the unbounded slice if isolated; however, the rule does not fire on bounded or chained slices, so this shape is silent—no hazard from misapplication.
  • If `seq` is annotated as a list but inferred as a subtype (e.g., `UserList`), and `copy()` is not overridden, the returned object may lack expected subclass behavior, though `list.copy()` on a subclass returns a plain list, whereas slicing may preserve subclass type—this is a behavioral change.
  • In code that depends on the slice returning exactly the same type as the input (e.g., for duck typing with custom sequences), replacing with `copy()` narrows the type to `list`, breaking polymorphism.
  • If the slice appears in a lambda or comprehension where the variable is rebound later (e.g., `[f() for x in data][:]` vs `[f() for x in data.copy()]`), the fix does not change behavior because the slice is evaluated immediately—but note: the rule does not fire on `data[:]` inside a comprehension index; it fires on standalone unbounded slices.
