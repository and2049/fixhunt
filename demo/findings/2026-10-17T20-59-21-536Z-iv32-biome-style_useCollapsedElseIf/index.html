Rule analysis

Flags when an else block contains exactly one if statement as its sole content.

Fix: Replaces 'else { if(condition) {...} }' with 'else if(condition) {...}', preserving inner block structure and comments.

8 hazards
  • Moving a leading comment inside the else block to before the else if keyword changes its association from the inner if to the else clause, altering documentation intent.
  • If the else block contains a function declaration, hoisting behavior differs between block-scoped (else { function f(){} }) and else-if scoped (else if(...) function f(){}) declarations, potentially causing reference errors.
  • An empty else block ({}) after transformation would be invalid syntax, but the rule prevents this by requiring exactly one if statement.
  • When the inner if is labeled (e.g., else { label: if(x){} }), the label is lost during rewrite, breaking goto-like control flow via break/label.
  • If the else block starts with a directive prologue like 'use strict';, moving it before else if alters its scope from the else block to the else-if construct, potentially changing strict mode behavior.
  • Comments placed between the else brace and the inner if (e.g., else { /* comment */ if(){} }) are relocated to precede the else if, which may misalign them with subsequent code in minified outputs.
  • In environments with non-standard semantic whitespace sensitivity (e.g., certain DSLs or transpiled languages), removing braces could alter tokenization or parsing despite identical JS semantics.
  • If the inner if statement is part of a comma sequence (else { (0, if(x){}) }), the rewrite breaks invalid syntax but such cases are already parse errors; however, the rule assumes valid input where if is a statement, not an expression.
