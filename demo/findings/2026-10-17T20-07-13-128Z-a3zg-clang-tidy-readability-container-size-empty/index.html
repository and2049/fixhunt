Rule analysis

The rule flags comparisons of container size() to zero using == or != operators.

Fix: Replace 'container.size() == 0' with 'container.empty()' and 'container.size() != 0' with '!container.empty()'

12 hazards
  • The expression may have side effects if size() is overloaded with non-const or mutating behavior, and empty() may not replicate those effects.
  • If the container type lacks an empty() member function, the rewrite will fail to compile.
  • The return type of size() might be unsigned, and comparing to zero could trigger warnings that empty() avoids, but the logical equivalence holds only if size() accurately reflects emptiness.
  • In templates, empty() might be resolved via ADL or inheritance differently than size(), leading to different overloads being selected.
  • If size() is virtual and overridden in a derived class, empty() might not be overridden, breaking behavioral equivalence.
  • The rewrite may interfere with debugging or logging if size() has breakpoints or side effects absent in empty().
  • If the container is actually a range or view without an empty() method but with size(), the rewrite is invalid.
  • Comments attached to the original size() expression may be lost or misplaced during the rewrite.
  • The rewrite could change the expression's type if size() returns a proxy type with operator== defined but empty() returns a different type.
  • In constexpr contexts, size() and empty() might differ in evaluation eligibility due to implementation constraints.
  • If the container is a custom type where empty() has different complexity guarantees (e.g., O(n) vs O(1)), performance characteristics may change.
  • The macro expansion context might cause the rewrite to alter precedence if size() is part of a larger expression involving operators like ?, :, or ,.
