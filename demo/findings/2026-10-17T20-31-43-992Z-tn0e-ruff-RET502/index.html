Rule analysis

Flags bare 'return' statements in functions where at least one other return returns a non-None value.

Fix: Replace each bare 'return' statement with 'return None'.

10 hazards
  • Rewriting 'return' inside a generator function changes it from yielding nothing to yielding None, altering iterator output.
  • In async functions, 'return' becomes 'return None', which may affect awaited values if callers expect no return value.
  • If the bare 'return' is inside a nested function that is used as a context manager, returning None instead of implicitly returning None has no behavioral difference but could confuse static analysis tools expecting generator-like behavior.
  • If the function's return annotation is '-> None', adding explicit 'return None' is redundant but harmless; however, if annotation is missing or incorrect, it may mask type checker warnings about inconsistent return types.
  • If the bare 'return' occurs after a side-effecting expression (e.g., 'print(x); return'), moving 'None' into the return statement does not change side effects, but if the rewrite were mistakenly placed before the side effect due to incorrect line wrapping, it would alter execution order.
  • If the code contains a trailing comment on the same line as 'return' (e.g., 'return # early exit'), the rewrite may drop the comment if the tool does not preserve comments during token replacement.
  • If the bare 'return' is inside a lambda (though lambdas cannot contain bare returns), this shape cannot occur, but if mistakenly applied via macro-generated code, it would raise a SyntaxError.
  • In functions decorated with @property, @staticmethod, or @classmethod, the rewrite behaves identically since these decorators do not alter return value semantics.
  • If the function is overridden in a subclass and the bare 'return' is part of a contract expecting implicit None, making it explicit may improve clarity but does not change behavior.
  • If the code relies on the disassembly showing 'LOAD_CONST(None)' vs. implicit return, debugging or profiling tools that distinguish explicit vs. implicit returns may report different bytecode, though behavior is identical.
