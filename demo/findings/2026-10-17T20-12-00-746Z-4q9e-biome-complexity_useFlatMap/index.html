Rule analysis

The rule flags uses of .map() followed by .flat() where flat() has no argument or an explicit depth of 1, suggesting replacement with .flatMap() to avoid creating an intermediate array.

Fix: Replace the chained .map().flat() or .map().flat(1) call with a single .flatMap() call using the same mapping function, preserving all arguments and surrounding syntax.

8 hazards
  • If the map callback contains side effects that depend on intermediate array indices, removing the intermediate array may alter behavior if those indices are used elsewhere.
  • If the flat depth is omitted but the map returns nested arrays deeper than one level, flatMap only flattens one level, potentially leaving extra nesting compared to the original.
  • If the map function returns holes (empty slots), .flat() removes them while .flatMap() preserves them, changing array length and indices.
  • If the map function uses 'this' and the context is bound via .map(callback, thisArg), the fix must preserve the thisArg or it will be lost.
  • If the chain includes .map().flat() after a non-array method like .filter(), the fix only applies to the map-flat pair and must not disturb surrounding chain links.
  • If the map callback throws an exception, the timing of when that exception occurs relative to subsequent operations is unchanged, but any reliance on the intermediate array's existence for debugging or inspection is removed.
  • If the code relies on the intermediate array being a distinct object in memory (e.g., for identity checks via ===), replacing it with flatMap's internal optimization breaks such checks.
  • If the map function returns undefined, .flat() skips it while .flatMap() also skips it, so no change, but if it returns null, both treat it as a single element, so still safe—however, if the map returns a non-array scalar, both behave identically in flattening one level.
