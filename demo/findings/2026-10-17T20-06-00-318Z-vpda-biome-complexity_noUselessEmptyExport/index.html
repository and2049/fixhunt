Rule analysis

The rule flags unnecessary 'export {}' statements when another top-level import or export already exists in the same module.

Fix: The autofix removes the 'export {}' statement entirely, leaving the rest of the file unchanged.

8 hazards
  • Removing 'export {}' in a file with only that export turns the module into a script, potentially breaking top-level 'this' semantics and strict mode enforcement.
  • If the file relies on being a module for proper lexical scoping of top-level 'var' (which is not added to global in modules), removing the export could inadvertently expose 'var'-declared variables globally.
  • In environments sensitive to module vs script distinction (e.g., Chrome extensions, Web Workers), removing the export may alter loading behavior or security policies.
  • If the 'export {}' is followed by a comment that has semantic meaning (e.g., licensing, dependency metadata), its removal could strip important information even if the fix aims to preserve comments.
  • When using bundlers that treat empty exports as entry points or side-effect markers, removing it might affect tree-shaking or bundle inclusion logic.
  • If the file is intended to be imported solely for its side effects and the 'export {}' ensures module status, removing it could cause the file to be treated as a script, altering execution context.
  • In TypeScript, removing the empty export may affect how the file is interpreted in ambient contexts or declaration merging, though less likely at term level.
  • If the 'export {}' appears after a top-level await, removing it does not change module status (since await already makes it a module), but the fix still applies and is safe—however, this is not a hazard; instead, note that the fix remains safe even then.
