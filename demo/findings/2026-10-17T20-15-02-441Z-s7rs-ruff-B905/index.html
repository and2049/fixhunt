Rule analysis

Flags uses of zip() with multiple arguments lacking an explicit 'strict' parameter.

Fix: Adds ', strict=True' to the zip call's argument list before the closing parenthesis.

12 hazards
  • Adding strict=True changes behavior when iterables have unequal lengths by raising ValueError instead of truncating, potentially causing crashes where code previously continued silently.
  • If the zip result is never consumed (e.g., in a tuple or list context that isn't evaluated), the strict check may never trigger, making the fix ineffective in lazy contexts.
  • When zip appears inside a larger expression (e.g., f(zip(a, b))), inserting strict=True alters the argument list and could break if the function f has a strict parameter or if positional semantics are relied upon.
  • If the zip call spans multiple lines with trailing comments, the fix may misplace the inserted argument relative to comment indentation or line continuation.
  • In code using star-args like zip(*vars), the fix inserts strict=True after the unpacked args, which may conflict if vars itself contains a value named strict or if the unpacking order is semantically significant.
  • If zip is overridden locally (e.g., def zip(...): ...), the fix assumes the built-in zip signature and may incorrectly modify a custom function call.
  • When zip is used in a default argument (e.g., def f(x=zip(a, b)):), the fix evaluates zip at definition time, potentially raising ValueError early if iterables unequal, altering when errors occur.
  • If the zip call is part of a tuple assignment like a, b = zip(*pairs), inserting strict=True changes the zip call but not the unpacking, which may hide length mismatches until iteration.
  • In comprehensions like [x for x in zip(a, b)], the fix adds strict=True but the comprehension may still swallow ValueError if not handled, differing from error propagation expectations.
  • If zip appears in a string or comment (e.g., '# see zip(a, b)'), the fixer might incorrectly modify it due to flawed AST-to-source mapping, corrupting non-code text.
  • When zip is called via attribute access like itertools.zip_longest(a, b) mistakenly flagged (though rule shouldn't fire), applying the fix would be nonsensical; but within rule scope, false positives could inject strict into unrelated calls.
  • If the zip call is generated by a macro or codegen tool, inserting strict=True may produce invalid syntax if the generator doesn't expect extra arguments.
