Rule analysis

The rule flags `<link>` elements pointing to `https://fonts.gstatic.com` without a `rel="preconnect"` attribute.

Fix: Adds the attribute `rel="preconnect"` to the `<link>` element if it is missing; if other `rel` values are present, they are preserved and `preconnect` is added as an additional value (e.g., `rel="preload preconnect"`).

8 hazards
  • Adding `preconnect` to `rel` may conflict with existing values like `stylesheet` if the browser prioritizes one over the other, potentially altering resource loading behavior.
  • If the `<link>` tag is inside a conditional comment or template literal that is not parsed as HTML, the rewrite could break syntax or produce invalid markup.
  • The fix may duplicate `preconnect` if the attribute already exists in a different case (e.g., `rel="PreConnect"`), leading to redundant or non-standard values.
  • In JSX, if the `rel` value is dynamically generated via an expression (e.g., `rel={condition ? 'preload' : ''}`), the static rewrite cannot safely inject `preconnect` without risking incorrect runtime values.
  • If the `<link>` element is rendered via `dangerouslySetInnerHTML`, the autofix cannot modify the internal string, so the fix would be inapplicable or misapplied.
  • Moving or dropping comments inside the `<link>` tag (e.g., `<!-- preconnect -->`) during rewrite could remove developer annotations or conditional debugging flags.
  • When the `href` value is constructed via string concatenation or variables (e.g., `href={"https://fonts.gstatic.com" + suffix}`), the rule may incorrectly fire or fail to recognize the target, leading to false positives or missed fixes.
  • In server-side rendering contexts, adding `preconnect` may alter the order of resource hints in the head, potentially affecting how browsers prioritize early connections versus other resources.
