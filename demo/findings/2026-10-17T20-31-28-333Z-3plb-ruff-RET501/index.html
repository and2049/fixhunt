Rule analysis

Flags explicit 'return None' statements where None is the only possible return value across all code paths in a function.

Fix: Rewrites 'return None' to 'return' when None is the only possible return value across all code paths in the function.

8 hazards
  • The rewrite removes trailing comments attached to the return statement, altering source code readability.
  • If the function contains a docstring after the return statement (unreachable but syntactically valid), the rewrite may affect parsing in edge cases involving AST transformations.
  • In rare cases where 'return None' is used to deliberately suppress a generator yield (though syntactically invalid as mixed yield/return), the rewrite could interfere with tooling expectations.
  • If the return statement is part of a larger expression via line continuation (e.g., using backslash), rewriting may break syntax due to changed token structure.
  • The fix may interfere with custom decorators or metaclasses that inspect bytecode offsets, as removing 'None' alters the bytecode length and jump targets.
  • In debugging contexts, explicit 'return None' may be used to set breakpoints; removing it could affect debug symbol mapping.
  • If the function is overridden in a subclass and the return type is part of a contract (e.g., via structural typing), changing the return may affect type checker inferences.
  • The rewrite may eliminate a deliberate 'return None' used to avoid returning a tuple in a single-expression function where implicit return would otherwise produce None anyway—no behavioral change, but may violate stylistic intent in codebases that enforce explicit returns for clarity.
