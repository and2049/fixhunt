Rule analysis

Flags unnecessary else blocks containing only pass or ellipsis statements.

Fix: Removes the else block entirely, dedenting any following code to the same level as the if/while/for/try statement.

12 hazards
  • The else block may contain a docstring or comment that provides important context or API documentation, which would be lost upon removal.
  • If the else block is part of a try-except-else-finally construct, removing it could alter control flow when no exception occurs, potentially skipping cleanup or logging intended for the success path.
  • In nested conditional structures, removing an else block could change the indentation of subsequent code, causing it to be incorrectly associated with an outer block.
  • The pass or ellipsis statement might be intentionally used as a placeholder for future implementation; removing it could obscure developer intent or break code generation tools that rely on its presence.
  • If the else block is followed by a comment on the same line or inline, that comment may be incorrectly attached to the preceding block or lost during rewriting.
  • In code that relies on the else block for structural symmetry (e.g., code generation or templating), its removal could break expected patterns or formatting rules.
  • The rewrite assumes the else block is syntactically isolated; however, if it contains only a trailing comment after pass/..., the comment's association may be misinterpreted during parsing.
  • In interactive or debugging contexts, the else block might host a breakpoint via pass; removing it could eliminate a deliberate stop point for debugging.
  • If the else block is part of a one-line compound statement (e.g., 'if x: y()\nelse: pass'), the fix may not apply due to formatting constraints, but if forced, could disrupt line-based tooling like coverage or blame.
  • The removal could affect tools that track cyclomatic complexity or code coverage metrics, as the else branch—even if empty—may be counted as a testable path.
  • In rare cases, the else block might be present to satisfy a syntactic requirement in a macro-generated or metaprogrammed context where empty branches are significant.
  • If the else block is immediately followed by a decorator or class/function definition at the same indentation level, removing it could cause misalignment in the AST, leading to incorrect binding of subsequent definitions.
