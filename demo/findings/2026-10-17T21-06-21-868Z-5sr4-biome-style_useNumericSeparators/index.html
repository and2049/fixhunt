Rule analysis

The rule flags integer and floating-point literals lacking digit group separators according to configurable minimum length and group size.

Fix: Inserts underscores as digit separators starting from the least significant digits, grouping according to the rule's groupLength option for the literal's base, only when the total digit count meets or exceeds minimumDigits.

11 hazards
  • In template literals like `${12345}`, inserting separators changes the evaluated string value because digits are altered.
  • In tagged template literals such as `str`12345`ess`, the raw string received by the tag function differs, potentially changing the tag's output.
  • When a numeric literal is part of a larger identifier via concatenation like `"num" + 12345`, the fix changes the resulting string from "num12345" to "num12_345".
  • If the literal appears in a comment-assisting context such as `// value: 12345 → process()`, moving or altering the literal breaks the comment's accuracy.
  • In regex literals containing digit patterns like `/12345/`, the rule does not apply, but if misapplied would break the pattern; however, the fix only targets standalone literals, so this is not a direct hazard—yet adjacent slashes could be confused during tokenization if whitespace is mishandled.
  • In legacy octal literals like `0644` (invalid in strict mode), the rule does not fire, but if mistakenly processed, inserting separators would yield `0_6_4_4`, which is not a valid octal literal and causes a syntax error.
  • When the literal is inside a JSX text node such as `<Text>12345</Text>`, the rule does not apply because it's not a JS expression, but if incorrectly targeted, the UI would render "12_345" instead of "12345".
  • If the literal is a boundary case like `12345` and groupLength is 2, producing `1_23_45`, a subsequent dot access like `(1_23_45).toString()` remains valid, but if the literal were mistakenly applied to a property access chain such as `obj.12345` (invalid syntax), no fix occurs because it's not a literal.
  • In eval contexts like `eval("12345")`, the fix does not apply because the literal is inside a string, but if the string were rewritten, the evaluated result changes from 12345 to 12_345 (invalid syntax) or, if parsed as separate tokens, may throw.
  • When the literal has leading zeros such as `0012345` (treated as decimal 12345), inserting separators yields `00_12_345`, which is still a valid decimal literal but may be unexpected if the leading zeros were semantically meaningful (e.g., for padding).
  • In automatic semicolon insertion scenarios, if the fix introduces a line break due to formatting changes (though it doesn't), it could affect ASI—but the fix only inserts underscores, so line structure is preserved.
