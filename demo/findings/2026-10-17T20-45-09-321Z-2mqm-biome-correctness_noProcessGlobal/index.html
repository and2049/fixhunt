Rule analysis

Flags any direct reference to the `process` global variable.

Fix: Replaces every occurrence of the identifier `process` with an imported binding by adding `import process from 'node:process';` at the top of the file (if not already present) and rewriting the reference to use that imported binding.

8 hazards
  • Replacing `process` in a catch clause like `catch (process)` would rename the exception parameter, altering what is caught.
  • If a local variable named `process` is declared later in the same scope, the import would hoist above it and cause the local variable to shadow the import instead of the global, changing runtime behavior.
  • When `process` is used as a label (e.g., `process: break process;`), the rewrite would break syntax because labels cannot be replaced with imported identifiers.
  • In indirect eval calls such as `eval('process.env')`, the string is not rewritten, so the eval would still resolve to the global `process` if it exists, diverging from the direct-reference behavior.
  • If the file already contains an import named `process` from a different source (e.g., `import process from './local-process'`), adding another import would cause a duplicate identifier error.
  • When `process` is accessed via destructuring with a default value like `{process = fallback} = obj`, the rewrite would fail to produce valid syntax.
  • Comments attached to the `process` token (e.g., `process/* TODO */.env`) would be lost because the autofix replaces the entire token without preserving trailing or inline comments.
  • In non-ESM environments where `import` statements are not supported (e.g., CommonJS without `type: module`), inserting the import would cause a parse error or runtime failure.
