Rule analysis

Flags unnecessary dict(), list(), or tuple() calls without arguments that can be replaced by empty literal syntax.

Fix: Replaces dict() with {}, list() with [], and tuple() with () when called with no arguments.

9 hazards
  • Rewriting dict() to {} may drop inline comments attached to the call expression if they are not preserved during AST transformation.
  • If dict is locally rebound (e.g., `dict = lambda: None`), replacing dict() with {} changes semantics because the literal invokes the built-in dict type, not the local binding.
  • In rare cases involving import hooks or metaprogramming that intercept built-in name resolution, replacing dict() with {} bypasses the hook, altering behavior.
  • If the code relies on the traceback showing a call to 'dict()' for debugging or logging, replacing it with {} removes that call frame, affecting diagnostic output.
  • When dict() appears in a string literal or comment (e.g., 'print("dict()")'), the autofix must not trigger, but a buggy implementation might erroneously modify such strings.
  • If dict() is used in a context where its return value is intentionally ignored for side effects (though dict() has none), replacing it with {} could mislead readers about intent, though no behavioral change occurs.
  • In code that is parsed and then executed via exec() or eval() with a restricted globals where dict is removed, replacing dict() with {} may succeed where the original would raise NameError, altering error behavior.
  • If the code depends on the exact bytecode or memory allocation pattern of calling dict() vs. using {} (e.g., for benchmarking or low-level optimization), the rewrite changes those characteristics.
  • When dict() appears in a DSL or code-generation context where the text 'dict()' is later interpreted by another system, replacing it with {} breaks downstream processing.
