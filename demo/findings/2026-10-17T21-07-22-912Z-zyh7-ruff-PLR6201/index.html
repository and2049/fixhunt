Rule analysis

Flags membership tests using list or tuple literals where a set literal would be more efficient.

Fix: Replaces the list or tuple literal on the right-hand side of a membership test with an equivalent set literal containing the same elements.

12 hazards
  • Rewriting [1, 2, [3]] to {1, 2, [3]} raises TypeError due to unhashable list element.
  • Rewriting [(1,2), (3,4)] to {(1,2), (3,4)} is safe only if tuples are hashable, but fails if tuples contain unhashable items like lists.
  • Rewriting [] to set() changes the type from list to set, which may break code relying on list-specific methods or ordering.
  • Rewriting () to set() loses the ability to distinguish empty tuple from empty set in isinstance checks or pattern matching.
  • If the left-hand side is unhashable (e.g., a list), rewriting [1,2] to {1,2} causes TypeError during membership test even if original would have returned False.
  • The fix may reorder elements due to set's unordered nature, breaking code that depends on iteration order of the literal in subsequent expressions (though rare in pure membership).
  • Comments attached to the list/tuple literal (e.g., x in [1, # comment 2]) may be lost or misplaced during rewrite.
  • In rare cases, if the literal contains duplicate elements, the set literal removes them, changing the logical meaning if duplicates were intended (though membership test behavior is identical for duplicates).
  • If the literal is used elsewhere in the same expression (e.g., x in [1,2] and [1,2].append(3)), the rewrite breaks aliasing or mutation expectations.
  • Rewriting a tuple literal to a set literal may interfere with unpacking or star expressions in larger contexts if the literal is reused (though rule only triggers on simple membership).
  • The fix may interfere with debugging or tracing tools that rely on the identity or type of the literal object.
  • If the literal appears in a string or comment nearby, the rewrite could create confusion or false positives in manual code review.
