Rule analysis

Flags 'else' blocks that follow an 'if' containing a breaking statement (return, break, continue, throw), marking them as redundant.

Fix: Removes the 'else' keyword and braces, promoting the else block's statements to the same indentation level as the if statement, preserving their original order.

12 hazards
  • Moving statements from an else block to the outer scope changes their execution context—they may now run even when the if condition is true but non-breaking (e.g., due to missing break/return).
  • If the else block contains a variable declaration with 'let' or 'const', hoisting it outward may cause a ReferenceError if used before declaration in the new scope.
  • Promoting statements from an else block can alter evaluation order relative to prior or subsequent statements in the enclosing block, affecting side effects.
  • If the else block contains a labeled statement that is referenced by a break/continue from outside the original else, moving it may break the label's visibility or create incorrect control flow.
  • When the if-else is inside a loop, promoting the else block's content may cause it to execute on iterations where the if condition is true but doesn't break (e.g., continues), altering loop behavior.
  • If the else block contains a function declaration, moving it may change its hoisting timing relative to other declarations in the outer scope, leading to override issues.
  • Comments attached to the 'else' keyword or its braces may be lost during the rewrite, as the autofix typically discards irrelevant tokens.
  • If the else block is empty or contains only whitespace/comments, removing it may inadvertently delete meaningful formatting or trailing comments relied upon for readability or tooling.
  • In strict mode, promoting a 'with' statement (if present) from an else block could alter scope resolution unexpectedly.
  • If the else block follows an 'if' inside a with statement, moving its content out may change the object scope in which those statements execute.
  • When the if statement is part of a larger ternary-like chain via else-if, flattening may break the intended mutual exclusivity of branches.
  • If the else block contains a debugger statement, its removal or relocation may affect debugging behavior depending on tool expectations.
