Rule analysis

Flags redundant round() calls where the second argument is zero and the first argument evaluates to an integer.

Fix: Replaces round(expr, 0) with expr when expr is statically known to be an integer (e.g., literal int, bool, or expression of integer-typed constants).

10 hazards
  • If expr has side effects (e.g., a function call), removing round may alter evaluation timing relative to other expressions.
  • If expr is a variable whose type cannot be statically proven as int, the fix may incorrectly apply at runtime for non-int values (e.g., float).
  • If expr is a boolean, replacing round(bool, 0) with the bool changes the type from int to bool, potentially breaking downstream int-specific operations.
  • If expr is used elsewhere in the same line, removing round may affect operator precedence or grouping (e.g., in round(a+b, 0)*2 vs (a+b)*2).
  • If round appears in a larger expression where its return value is ignored, deleting it may preserve value but alter side-effect visibility in debugging or tracing tools.
  • If the code relies on round returning a float subclass (unlikely but possible via overrides), replacing with expr may change the return type.
  • If expr is a constant that overflows in int context but not in float, the transformation could change value (though Python ints are arbitrary precision, this is negligible).
  • If the round call is inside a lambda or comprehension, removing it may affect JIT or optimization assumptions in some implementations.
  • If comments are attached to the round call (e.g., # tolerance), the fix may discard them if not preserved during rewrite.
  • If expr is a named expression (walrus) like round((y := f()), 0), removing round may change the scope or timing of y's assignment.
