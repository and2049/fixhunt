Rule analysis

Flags unnecessary initializations of variables to `undefined`, since they receive that value implicitly.

Fix: Removes the `= undefined` initializer from variable declarations while preserving other declarators in the same statement and moving any inline comments to the end of the declaration.

11 hazards
  • In a `for` loop initializer like `for (let i = 0, j = undefined; i < n; i++)`, removing `= undefined` may alter the evaluation order if the omitted initializer had side effects (though `undefined` is literal, Biome treats it as removable only when isolated).
  • If a variable declaration with `= undefined` is inside a `with` statement, removing the initializer could change scope resolution if the variable name matches a property in the with object.
  • In non-strict mode, a variable named `undefined` could be reassigned, but the rule only flags explicit initialization to the literal `undefined`, so the fix remains safe as it doesn't affect the global `undefined` binding.
  • When a declaration like `let x = undefined, y = foo();` is split across lines with a comment after `undefined`, the fix moves the comment to the end of the line, potentially changing its visual association though not its syntactic validity.
  • In a `try` block, if `let x = undefined;` is followed by a `return` statement, removing the initializer does not affect control flow since the assignment of `undefined` is a no-op.
  • In a comma-separated declaration like `var a = undefined, b = 1;`, removing `= undefined` results in `var a, b = 1;`, which is valid and equivalent because `a` is still implicitly `undefined`.
  • If the code relies on the temporal dead zone (TDZ) behavior of `let` or `const`, removing an explicit `= undefined` does not change TDZ semantics since the variable is still not accessed before declaration.
  • In a function parameter default like `function f(x = undefined)`, the rule does not trigger, so no fix is applied; thus, no hazard arises from confusing parameter defaults with variable initializers.
  • In a class field like `class C { f = undefined; }`, the rule does not trigger (as per valid examples), so no fix is attempted, avoiding incorrect removal of meaningful initializations.
  • If a declaration contains a trailing comma after the initializer (e.g., `let x = undefined,`), removing `= undefined` may leave a dangling comma, but Biome's formatter handles this by adjusting the syntax appropriately during the fix.
  • In a destructuring pattern like `let [a = undefined] = [];`, the rule does not currently flag this (per documentation focus on simple initializations), so no fix is applied, preventing incorrect simplification of destructuring defaults.

r1-p005 fix-changes-behaviorlabelled safejudge: real · high Var Hoisting and Redeclaration in Loop

The fix removes the explicit `= undefined` initializer from a `var` declaration inside a loop. Because `var` is function-scoped, the original code re-initializes `a` to `undefined` on every iteration, while the fixed code leaves `a` uninitialized only on the first iteration and then retains the previous iteration's value. This changes the observable output from `undefined, undefined` to `undefined, 0`, a silent wrong result in plausible code.
