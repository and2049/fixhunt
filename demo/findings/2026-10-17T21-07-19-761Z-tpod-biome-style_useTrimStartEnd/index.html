Rule analysis

Flags calls to String.trimLeft() and trimRight() and suggests replacing them with the semantically identical but preferred String.trimStart() and trimEnd().

Fix: Replaces .trimLeft() with .trimStart() and .trimRight() with .trimEnd(), preserving all surrounding syntax including method call parentheses and any chained expressions.

11 hazards
  • The rewrite assumes the base expression is a string; if it is not, both the original and rewritten code will throw a TypeError at runtime, so behavior is preserved but errors may occur where none were expected.
  • If the method is accessed via a property name that is dynamically computed (e.g., obj[method]()), changing the hardcoded name from 'trimLeft' to 'trimStart' alters which property is looked up, potentially causing a different function to be called or undefined to be invoked.
  • If the code relies on the method being non-enumerable or having specific descriptors (unlikely for built-ins), the rewrite does not affect descriptors since it only changes the identifier used in property access.
  • In rare cases where trimLeft or trimRight has been overridden on String.prototype or an instance, the rewrite bypasses the override by calling the standard trimStart/trimEnd methods, altering behavior.
  • If the call is part of a larger expression with side effects (e.g., in a logical chain like foo && bar.trimLeft()), the rewrite does not change evaluation order or side-effect timing.
  • Comments attached directly to the method name (e.g., trimLeft/*comment*/()) would be lost because the autofix replaces the entire identifier, stripping any inline comments.
  • If the code uses a with statement that binds a variable named trimLeft or trimStart, the lookup semantics could differ, though with is deprecated and rarely used.
  • In strict mode, if trimLeft or trimStart is mistakenly referenced as a variable due to a typo, the rewrite could turn a ReferenceError into a valid method call (or vice versa), but this is outside the rule's scope as it only applies to property accesses.
  • If the base expression evaluates to an object with a custom trimLeft property that is not a function (e.g., a getter with side effects), replacing the property name changes which getter is invoked.
  • The autofix does not preserve trailing whitespace or formatting inside the method call parentheses (which are empty anyway), so no behavioral impact there.
  • If the method is called via optional chaining (e.g., foo?.trimLeft()), the rewrite correctly preserves the optional chaining operator, so no hazard arises from that form.
