Rule analysis

Flags imports of 'node:assert' to recommend using 'node:assert/strict' instead.

Fix: Replaces the module specifier 'node:assert' with 'node:assert/strict' in import or require statements while preserving the import kind (Namespace, Default, Named, etc.) and all syntactic structure except the string literal value.

12 hazards
  • If the code relies on non-strict assertion behavior (e.g., `assert.ok(0, 0)` being treated as truthy), switching to strict mode may cause assertions to throw where they previously did not, altering control flow.
  • If the imported `assert` is reassigned to a variable used in dynamic import expressions (e.g., `import(`${assert}`)`), changing the source string could break module resolution if the bundler or runtime depends on the literal value.
  • If the import statement contains trailing or inline comments (e.g., `import * as assert from "node:assert" /* reason */;`), the autofix may drop or misplace them depending on the tool's comment handling.
  • If the module specifier is constructed via concatenation (e.g., `import * as assert from "node:" + "assert"`), the rule does not fire, but if it did fire incorrectly, the fix would break because it assumes a literal string.
  • If the code uses `assert` as a namespace object and expects non-strict methods like `assert.equal` to coexist with strict ones, the strict module may lack certain legacy aliases, causing runtime errors.
  • If the import is wrapped in a conditional block (e.g., `if (true) { import * as assert from "node:assert"; }`), the fix preserves the block but changing the module may affect runtime behavior if the conditional guards side effects.
  • If the import is used for its side effects only and the binding is unused (e.g., `import "node:assert"`), the rule does not flag it, but if misapplied, changing the string could fail to load the module if `node:assert/strict` has different side effects.
  • If the codebase uses a custom module resolver or plugin that treats `node:assert` and `node:assert/strict` differently (e.g., for mocking), the rewrite could bypass intended mocks or aliases.
  • If the import occurs in a file that is both ES module and CommonJS transpiled (e.g., via Babel), the rewrite may produce inconsistent output depending on the target format.
  • If the assert import is reexported (e.g., `export * from "node:assert"`), changing the source may alter the reexported API surface if the strict module omits certain exports.
  • If the code depends on the exact string "node:assert" appearing in stack traces or error messages (e.g., via `new Error().stack`), changing the import source may affect diagnostic output.
  • If the import is part of a sequence where evaluation order matters (e.g., `import * as assert from "node:assert"; var x = assert.enabled;`), the fix preserves order but if `node:assert/strict` initializes differently, it could change timing.
