Rule analysis

Flags explicit len() comparisons where truthiness of a sequence alone suffices.

Fix: Replace 'len(seq)' with 'seq' directly, preserving any logical negation (!= becomes implicit falsy check, == 0 becomes 'not seq'), and drop the call while keeping surrounding operators/structure intact.

10 hazards
  • len() on a non-sequence type like int has no truthiness equivalent, causing TypeError if rewritten.
  • len() inside a lambda or comprehension may capture different variables if rewritten naively due to scope changes.
  • If len() appears in a macro-generated line via exec/eval, removing it alters the string source and can break dynamic execution.
  • When len() is part of a larger expression like 'len(a) + len(b)', rewriting only one side changes arithmetic meaning.
  • If the sequence variable is reused later and mutated, evaluating it twice (once for len, once for truthiness) could differ if the object's __len__ has side effects.
  • Rewriting drops any inline or trailing comments attached to the len() call, violating comment preservation expectations.
  • In a try/except block, if len() raises AttributeError on a None, rewriting to 'seq' raises the same error earlier but may shift blame line numbers.
  • If the sequence is a property with a getter that has side effects, calling it twice (once in original len, once in rewrite) vs once changes behavior.
  • In a boolean context wrapped by parentheses like '(len(x))', dropping len alters grouping if the expression is used in a bitwise context like '&'.
  • When len() compares to a non-zero constant like 'len(x) == 3', the fix incorrectly replaces it with 'x == 3' which is invalid.
