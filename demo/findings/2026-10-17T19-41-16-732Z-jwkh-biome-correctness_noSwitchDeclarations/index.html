Rule analysis

The rule flags any lexical declaration (`const`, `let`, `class`, or `function`) directly inside a `case` or `default` clause of a `switch` statement without being wrapped in a block.

Fix: Wraps the lexical declaration(s) in the problematic `case` or `default` clause in a block by adding `{` before the first declaration and `}` after the last statement in that clause, preserving all existing statements and their order.

11 hazards
  • If the clause contains a labeled statement, wrapping it in a block changes the label's scope, potentially breaking `break` or `continue` references to that label from outside the block.
  • If the clause contains a `break` statement with a label that refers to an outer loop, inserting a block does not affect the label resolution, but if the label is defined inside the clause, the block alters its scope and may cause the label to be undefined.
  • If the clause contains a `with` statement, introducing a block changes the scope chain for the `with` body, potentially altering variable resolution.
  • If the clause contains a `try`/`catch`/`finally` block, adding an outer block does not change behavior, but if the `catch` or `finally` clause declares variables with the same name as the hoisted declaration, the original code might have allowed access due to function-scoped hoisting, whereas the block prevents it.
  • If the clause contains a `return` statement, wrapping it in a block does not change the return value or control flow, but if the function is an arrow function with a concise body, the insertion of a block may require adding explicit `return` and braces, though this rule does not apply to arrow functions directly in switch clauses as they are expressions.
  • If the clause contains a `debugger` statement, adding a block around it does not affect its execution.
  • If the clause contains a comment immediately after the opening brace of the inserted block, the formatter might reposition it, but Biome's autofix aims to preserve comments; however, if comments are attached to the lexical declaration node, moving the declaration into a block could detach leading/trailing comments if not handled properly.
  • If the clause is the last clause in the switch and ends with a `break`, adding a block before the `break` does not affect semicolon insertion, but if the `break` is omitted and the clause falls through, the block does not change fall-through behavior.
  • If the lexical declaration is a `function` declaration, the original code hoists the function to the function scope, making it accessible throughout the switch (and function), while the fix makes it block-scoped to the case, so any reference to the function in other cases becomes a ReferenceError, changing behavior.
  • If the lexical declaration is a `class` declaration, similar to `function`, it is hoisted and accessible in the entire switch in the original code, but the fix restricts it to the block, so usage in other cases fails.
  • If the lexical declaration is a `const` or `let` with an initializer that has side effects (e.g., a function call), the original code evaluates the initializer only when the clause is reached, and the fix preserves this timing, so no change in evaluation timing occurs.
