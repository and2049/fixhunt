Rule analysis

Flags 'or' expressions where one operand is the logical negation of the other, such as 'x or not x', which always evaluates to True.

Fix: Rewrites the expression to the literal True, preserving any surrounding expression structure but replacing the entire 'or' expression with True.

8 hazards
  • The rewrite removes any side effects from evaluating the left operand first, such as in a function call with mutable state changes.
  • If the left operand is a property accessor (__getattr__ or __getattribute__), its side effects are lost when replaced with True.
  • When the operand is an indexing operation like lst[i], any __getitem__ side effects or exceptions are eliminated by the rewrite.
  • In chained comparisons like (x < y) or not (x < y), the rewrite removes the evaluation of x and y entirely, altering behavior if they have side effects.
  • If the expression appears in a context relying on its specific truthy value for type narrowing (e.g., in an if condition), replacing with True may affect static analysis but not runtime behavior—yet this is still a semantic shift in expression value.
  • Comments attached to the operands or operator (e.g., x # comment or not # comment x) may be lost during the AST rewrite.
  • In rare cases where the expression is used via eval() or exec() with dynamically scoped names, the rewrite could alter name resolution if operands contain undefined variables that would have raised NameError.
  • If the operand is a short-circuiting expression itself (e.g., f() or g()), the rewrite prevents evaluation of the right-hand operand in the negation, removing potential side effects from g().
