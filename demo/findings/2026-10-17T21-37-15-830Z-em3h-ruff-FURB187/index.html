Rule analysis

Flags inefficient list reversal patterns like assignment via slicing, reversed(), or list(reversed()) when .reverse() could be used.

Fix: Replaces the assignment target variable with an in-place .reverse() call on the same variable, e.g., 'l = l[::-1]' becomes 'l.reverse()'.

12 hazards
  • If the list is aliased elsewhere (e.g., another variable references the same list), mutating via .reverse() affects all aliases, whereas slicing creates a new list leaving original aliases unchanged.
  • If the reversed result is used immediately in an expression (e.g., function call), replacing with .reverse() breaks because .reverse() returns None, altering return values or side effects.
  • If the assignment is part of a larger expression (e.g., tuple unpacking or conditional), rewriting to a statement changes syntax and may cause invalid Python.
  • If the variable is deleted or reassigned later, the timing of mutation vs. creation affects memory usage and reference counting, potentially impacting __del__ methods or weakrefs.
  • If the list contains mutable elements and the code relies on the original list being unchanged for later use, .reverse() causes premature mutation.
  • If the slice operation includes step or bounds (e.g., l[::-1] vs l[1:5:-1]), the fix incorrectly applies .reverse() which only does full reversal, changing semantics.
  • If the variable is a property or item assignment (e.g., self.lst = self.lst[::-1]), the fix cannot be applied as .reverse() requires a direct variable name, not an attribute or subscript.
  • If the code depends on the identity of the list object (e.g., checking 'l is original' after reversal), .reverse() preserves identity while slicing creates a new object, breaking identity checks.
  • If the reversed list is iterated over before reassignment (e.g., for i in l[::-1]: ...; l = l[::-1]), moving .reverse() earlier changes iteration order due to premature mutation.
  • If the list reversal is guarded by a condition (e.g., if flag: l = l[::-1]), the fix must stay within the block; extracting .reverse() out of scope breaks conditioning.
  • If the variable is used in a lambda or comprehension after reversal but before reassignment, early mutation via .reverse() alters the iterable seen by the lambda/comprehension.
  • If the assignment occurs in a class or module level and the list is shared across instances or imports, in-place mutation introduces cross-instance state sharing bugs.
