Rule analysis

Flags calls to warnings.warn missing an explicit stacklevel argument.

Fix: Adds ', stacklevel=2' as the last positional or keyword argument before any existing keyword arguments like category or filename, preserving other arguments and their order.

10 hazards
  • If stacklevel was already provided as a positional argument after message (e.g., warnings.warn(msg, 1)), adding another stacklevel=2 creates a duplicate keyword argument, causing a TypeError.
  • If the call uses *args to pass arguments (e.g., warnings.warn(*args)), inserting stacklevel=2 breaks argument unpacking and may misalign parameters.
  • If the call is inside a lambda or comprehension where stacklevel affects outer scope lookup, forcing stacklevel=2 may alter which warning is suppressed by filters.
  • If warnings.warn is monkey-patched or overridden locally, the fix assumes the original signature and may pass an unexpected keyword argument.
  • If the code relies on the default stacklevel=1 behavior to show the warning origin at the warn site, changing it to 2 shifts blame to the caller, altering diagnostic intent.
  • If the call includes skip_file_prefixes in Python <3.12, the fix incorrectly adds stacklevel=2 despite skip_file_prefixes being ignored, potentially conflicting with user intent.
  • If the message argument is an expression with side effects (e.g., warn(f(x))), reordering arguments to insert stacklevel=2 could change evaluation order if the fix incorrectly places it before the message.
  • If the call uses keyword-only arguments via *, such as warnings.warn(msg, *, category=Error), inserting stacklevel=2 before * causes a syntax error.
  • If the code depends on the warning being filtered based on stackline matching, changing stacklevel alters which frames are considered and may unexpectedly show or hide warnings.
  • If the call is in a stub (.pyi) file or conditional typing block, adding runtime arguments may violate type checker expectations or cause overload mismatches.
