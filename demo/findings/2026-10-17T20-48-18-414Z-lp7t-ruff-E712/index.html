Rule analysis

Flags equality comparisons (`==`, `!=`) to boolean literals `True` or `False`.

Fix: Replaces `expr == True` with `expr`, `expr != True` with `not expr`, `expr == False` with `not expr`, and `expr != False` with `expr`.

10 hazards
  • For `x == True`: if `x.__eq__` has side effects, replacing with `x` drops those effects.
  • For `x != True`: if `x.__ne__` has side effects, replacing with `not x` drops those effects and changes truth evaluation.
  • If `x` defines `__eq__` to return non-boolean (e.g., integer), `x == True` may be truthy/falsy differently than `x`.
  • If `x` defines `__eq__` returning a proxy object with custom `__bool__`, truth value may differ after rewrite.
  • When `x` is an instance with `__eq__` comparing to `True` via value (e.g., enum member), `is`-based logic would fail but `==` rewrite to `x` still uses `__eq__`—wait, no: the fix does NOT use `is`, it uses direct truth test, so this is actually a hazard: if user intended to check identity to `True` literal, the fix changes semantics.
  • If `x` is `None`, `None == False` is `False`, but `not None` is `True`—so `x == False` rewritten to `not x` flips meaning.
  • If `x` is `0`, `0 == False` is `True`, but `not 0` is `True`—same here; wait, `0 == False` is True, `not 0` is True: actually same. But `0 != False` is False, rewritten to `0` which is falsy → same? Wait: `x != False` → fix is `x`. For `x=0`: `0 != False` → `False` (since 0==False → True, so != is False). Fix: `x` → `0` → falsey → False. Same. But for `x=1`: `1 != False` → True (since 1==False → False). Fix: `x` → `1` → truthy → True. Still same? Actually yes for ints. Hazard only when `__eq__` overridden.
  • If the comparison appears in a larger expression without parentheses, operator precedence may change after rewrite (e.g., `x == True and y` → `x and y` vs original `(x == True) and y`).
  • If the comparison is part of a tuple or list literal, removing the comparison may alter whether the element is considered truthy in a surrounding `any()` or `all()` call.
  • If the comparison is inside a lambda or comprehension used later, the timing of evaluation may shift if the fix removes a function call that was previously guarded by the comparison structure.
