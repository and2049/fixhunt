Rule analysis

Flags except clauses containing duplicate or redundant exception types where one type subsumes another.

Fix: Removes redundant exception types from the except tuple, keeping only the most general (superclass) exception when a subtype is present, or deduplicates identical types, preserving the original order of non-redundant types.

12 hazards
  • Rewriting `except (Exception, ValueError):` to `except Exception:` changes behavior if the handler relies on `ValueError` being matched first for conditional logic inside the handler, though such logic is unreachable anyway.
  • If the except clause contains a comment after a redundant type like `except (Exception, # keep ValueError):`, the autofix may incorrectly remove or misplace the comment during tuple restructuring.
  • When the except clause is part of a larger compound statement with line continuations, the rewrite may alter formatting in a way that breaks parsing if the tool does not preserve exact whitespace or parentheses structure.
  • In code that uses stringized exceptions via `from __future__ import annotations`, the autofix might not correctly resolve forward references, leading to incorrect removal or retention of types.
  • If the except tuple contains a variable name that shadows an exception class (e.g., `ValueError = 5; except (Exception, ValueError):`), the rewrite incorrectly treats it as a type and may produce invalid syntax or change meaning.
  • The autofix may fail to recognize that a user-defined exception inherits from a built-in, leading to incomplete redundancy removal and leaving the code still flagged.
  • In nested try statements, rewriting an outer except clause may affect the control flow of inner handlers if exceptions are re-raised, though this is unlikely due to redundancy.
  • If the except clause is followed by a `finally` block, the rewrite does not affect finally execution, but removing redundant types could be misconstrued as altering exception propagation timing—though it does not.
  • When the except clause uses a bare `except:` (no arguments), the rule does not fire, but if mistakenly applied, the fix would break syntax by introducing an empty tuple.
  • If the code depends on the exact tuple object for introspection (e.g., storing the except clause via `inspect`), the rewritten tuple may differ in identity or content, affecting metaprogramming.
  • Autofix may leave a trailing comma in a singleton tuple (e.g., `except (Exception,):`) which is valid but may trigger style warnings in strict codebases.
  • In code processed by tools that rely on the AST node's exact source representation (e.g., certain refactoring tools), the rewritten source may break source-to-AST roundtripping.
