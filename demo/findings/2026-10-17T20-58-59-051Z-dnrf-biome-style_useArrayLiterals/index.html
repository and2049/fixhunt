Rule analysis

The rule flags uses of the Array constructor without exactly one numeric argument, recommending replacement with array literals.

Fix: Replace Array(...) calls with [...] containing the same arguments, preserving spread elements and argument order; replace new Array(...) similarly while dropping the 'new' keyword.

11 hazards
  • Rewriting Array(x) where x is non-numeric changes behavior: Array(undefined) becomes [undefined] instead of [], altering length and element values.
  • If Array is shadowed by a local variable, replacing Array(...) with [...] breaks the reference to the local binding, potentially changing the constructor used.
  • When Array(...) appears in a larger expression (e.g., return Array(...)), moving comments attached to the parentheses or arguments may alter comment placement relative to surrounding tokens.
  • In contexts like typeof Array(...) === 'function', replacing with [...] changes the result from 'object' to 'object' but may affect type checks relying on constructor identity in non-standard environments.
  • If the Array constructor call has trailing comments (e.g., Array(1, 2 /* comment */)), the autofix may drop or misplace those comments during rewrite.
  • Using Array(...) in a comma sequence (e.g., let x = Array(1), y;) risks breaking parsing if the fix removes necessary delimiters or alters precedence unexpectedly.
  • When Array(...) is used as a function argument (e.g., fn(Array(1, 2))), the fix preserves semantics only if Array is the global constructor; if redefined locally, the literal [] behaves differently.
  • In eval() or Function() constructor contexts, the rewritten literal may be parsed differently due to strict mode implications or reserved word handling.
  • If the argument to Array(...) is an expression with side effects (e.g., Array(f())), the fix evaluates f() once as before, but if the literal is placed in a different syntactic position, evaluation order relative to other expressions could shift.
  • For Array(...) with more than 2^32-1 arguments, the literal may fail silently or throw where the constructor would have succeeded, though both are practically infeasible.
  • In rare cases involving __proto__ manipulation, replacing Array(...) with [] may alter inheritance if the literal is assigned to a prototype property expecting Array instance traits.
