Rule analysis

Flags set() constructor called with a single list or tuple literal argument.

Fix: Rewrites set(L) where L is a list or tuple literal to {*L} if non-empty, otherwise set().

8 hazards
  • The rewrite drops inline or trailing comments attached to the set() call or its argument, as the autofix may not preserve comment nodes during AST transformation.
  • If the list or tuple literal contains mutable elements that are later modified, the resulting set may capture different object identities due to reconstruction via set literal, though values remain equal.
  • In rare cases involving custom __eq__ or __hash__ implementations, the order of element insertion during set literal construction could theoretically affect hash collision resolution, though final set equality is preserved.
  • If the argument is a tuple literal used elsewhere in the code (e.g., assigned to a variable), rewriting to a set literal severs that shared reference, potentially breaking aliasing expectations.
  • The autofix may incorrectly apply to set() calls generated via macros or code-generation tools where the list/tuple appears literal but is semantically dynamic, leading to incorrect static rewrites.
  • If the set() call is part of a larger expression where the original call's formatting or line breaks are significant (e.g., for diff tools or readability), the rewrite may alter whitespace in a way that breaks team formatting rules.
  • When the list or tuple literal contains duplicate elements, the set literal rewrite behaves identically, but intermediate steps in evaluation (like list creation) are skipped, which could matter in tracing or debugging contexts.
  • If the code relies on the set() constructor for its type (e.g., isinstance(x, set) after assignment), the rewrite still produces a set, so no behavioral change occurs—this hazard is included to emphasize that type preservation holds, unlike in unsafe cases.
