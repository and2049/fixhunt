Rule analysis

Flags direct calls to Object.prototype methods (hasOwnProperty, isPrototypeOf, propertyIsEnumerable) invoked on arbitrary objects.

Fix: Replaces obj.methodName(args) with Object.prototype.methodName.call(obj, args) for hasOwnProperty, isPrototypeOf, and propertyIsEnumerable; replaces obj.hasOwnProperty with Object.hasOwn when applicable per rule documentation.

11 hazards
  • Rewriting foo.hasOwnProperty("bar") to Object.prototype.hasOwnProperty.call(foo, "bar") changes behavior if foo is null or undefined, as the former throws a TypeError while the latter also throws but may be caught differently due to call stack differences.
  • If foo.hasOwnProperty is a non-function value (e.g., a number or string), the original code throws TypeError when invoked, but the fix attempts to call Object.prototype.hasOwnProperty.call which expects a function, preserving the error but altering the error path.
  • When foo is declared with let or const and used before initialization in the same block, the fix does not alter the TDZ error timing, but if the original relied on foo being accessible via a scope hole, the fix does not change that—however, no behavioral shift occurs here as both forms reference foo identically.
  • If foo is a proxy with a get trap that returns a non-function for hasOwnProperty, the original invokes the trap and then attempts to call the result, throwing TypeError; the fix bypasses the trap entirely by referencing Object.prototype directly, so the get trap is not triggered, altering observable behavior.
  • In strict mode, if foo.hasOwnProperty is accessed via a with statement (deprecated but possible), the original resolves foo in the with scope, while the fix references Object.prototype globally, potentially changing the base object if the with scope had an Object property.
  • The fix removes any opportunity for side effects in the retrieval of foo.hasOwnProperty—such as logging in a get trap or modifying state—because it no longer accesses the property on foo at all, whereas the original evaluates foo.hasOwnProperty as an expression before calling it.
  • If the code depends on the call stack showing foo.hasOwnProperty in traces (e.g., for debugging or error reporting), replacing it with Object.prototype.hasOwnProperty.call alters the stack trace, which could affect error handling logic that inspects stack frames.
  • When the argument "bar" is an expression with side effects (e.g., a function call), the evaluation order of arguments is preserved in the fix, but if the original relied on the this-value being evaluated after arguments (which it never is in JS), no change occurs—however, this is not a real hazard since this-binding always happens before argument evaluation in calls.
  • If foo is document.all in legacy browsers (which acts like undefined for == null but has special behavior), the original may behave inconsistently due to its [[Call]] semantics, while the fix uses standard Function.prototype.call, potentially altering behavior in edge cases involving IE-specific quirks.
  • If the code is parsed in a context where Object.prototype has been overridden (e.g., via iframe pollution or deliberate mutation), the fix uses the current Object.prototype, which may differ from the original object's actual prototype chain if inheritance was altered, though this affects both original and fix similarly since both rely on Object.prototype.
  • Comments attached to the original call site (e.g., foo.hasOwnProperty/*note*/("bar")) may be lost or misplaced during the rewrite if the autofix does not preserve trailing or inline comments, degrading code readability.
