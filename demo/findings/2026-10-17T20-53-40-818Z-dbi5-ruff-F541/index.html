Rule analysis

Flags f-strings that contain no placeholder expressions.

Fix: Rewrites the f-string literal by removing the leading 'f' (or 'rf'/'fr') prefix, converting it to a regular string literal (or raw string if applicable).

10 hazards
  • If the f-string is part of a docstring (e.g., immediately follows a function/class definition), removing the 'f' may preserve the docstring but Ruff marks the fix unsafe in such cases—however, if incorrectly applied, it could alter tooling that distinguishes docstrings by presence of 'f'.
  • In a line-continued context using backslash (e.g., `f"hello" \ f"world"`), removing the 'f' from one segment changes the type of that segment from f-string to str, potentially breaking concatenation semantics if the other segment relies on interpolation (though rule only fires when no segment has placeholders).
  • If the f-string contains escaped quote characters (e.g., `f"He said \"hi\""`), the fix preserves them correctly since they are literal in both f-string and regular string contexts.
  • When the f-string uses triple quotes (e.g., `f"""hello"""`), the fix produces a triple-quoted regular string, which behaves identically for content without placeholders or escape dependencies.
  • If the f-string is a raw f-string (e.g., `rf"\n"`), the fix removes the 'f' to yield `r"\n"`, preserving raw string behavior; however, if the original relied on f-string-specific raw processing (which doesn't differ from raw string for non-interpolated content), it is safe—but Ruff may still consider it hazardous due to prefix alteration.
  • If the f-string appears inside a larger expression where its type is used in overload resolution or isinstance checks (rare), changing it from f-string to str could theoretically affect behavior, though both are instances of str and share the same runtime type.
  • If the f-string is adjacent to another string literal without an operator (implicit concatenation) and only the f-string is modified (e.g., `f"hello" "world"` → `"hello" "world"`), the concatenation result remains unchanged as both are string literals.
  • If the f-string contains a comment inside (invalid syntax—comments cannot be inside string literals), this is not a concern; however, if the line has a trailing comment (e.g., `f"hi" # note`), the fix preserves the comment as it lies outside the literal.
  • If the f-string is generated via a macro or code‑generation tool that expects the 'f' prefix for later processing, removing it could break downstream tooling, though this is outside Python semantics.
  • If the f-string is part of a stub file (.pyi) and the fixer runs there, altering the literal may affect type checker expectations, though f-strings without placeholders are uncommon in stubs and behave identically as str.
