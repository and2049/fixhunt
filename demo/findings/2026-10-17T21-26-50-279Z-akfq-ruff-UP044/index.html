Rule analysis

Flags type annotations using Unpack[] from typing where PEP 646 star-expression syntax (*T) can be used instead.

Fix: Replaces Unpack[X] with *X in type annotations, preserving the surrounding syntactic context (e.g., *args: *tuple[int, ...]).

8 hazards
  • Rewriting Unpack[expr] to *expr changes the meaning if expr is not a type but a value, as *expr becomes an illegal starred expression outside function parameters or invalid syntax elsewhere.
  • If Unpack appears in a string annotation (e.g., "Unpack[T]"), the fix may incorrectly modify it, breaking forward references or causing syntax errors in evaluated annotations.
  • In nested generic contexts like Dict[str, Unpack[Tuple[int]]], rewriting to *Tuple[int] produces invalid syntax because * is not allowed inside bracket notation.
  • When Unpack is used as a variable name (e.g., Unpack = 5), the fix erroneously rewrites it to *5, which is invalid syntax and alters the identifier's meaning.
  • The fix may remove or misplace comments attached to the Unpack token (e.g., Unpack[# inline comment int]) due to token-based replacement without comment preservation.
  • In class bodies or module-level code, *expr is syntactically invalid unless in a function parameter list, so rewriting Unpack[T] there raises a SyntaxError.
  • If the code targets Python <3.11, using *T in type annotations may be unsupported by the interpreter or type checkers, even if semantically equivalent.
  • When Unpack is imported under an alias (e.g., from typing import Unpack as U), the fix may fail to trigger or incorrectly rewrite the alias, leading to inconsistent or missed transformations.
