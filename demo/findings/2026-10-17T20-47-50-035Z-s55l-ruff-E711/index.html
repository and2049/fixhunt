Rule analysis

Flags non-is comparison operations against None.

Fix: Replaces '==' with 'is' and '!=' with 'is not' when comparing against None literal.

12 hazards
  • If __eq__ is overridden, 'x == None' may differ from 'x is None', changing truth value.
  • If __ne__ is overridden, 'x != None' may differ from 'x is not None', altering logic flow.
  • Rewriting 'None == x' to 'None is x' fails if x defines __eq__ but not symmetric behavior via __eq__ delegation.
  • Comments attached to the operator (e.g., 'x == # comment\nNone') may be lost or misplaced during token replacement.
  • In expressions like 'f(x == None)', rewriting changes operand type from bool to NoneType, breaking function expectations.
  • If None is shadowed locally (e.g., 'None = 5'), the fix incorrectly rewrites to 'is 5' or 'is not 5', causing NameError or wrong semantics.
  • In default arguments like 'def f(x=None): if x == None:', the fix alters comparison but not the default, creating inconsistency if None is rebound.
  • When used with Optional types in generics, 'x == None' might rely on overloaded equality in proxies, which 'is' bypasses.
  • In NumPy arrays, 'arr == None' returns an array of bools, while 'arr is None' is always False — rewrite breaks vectorized intent.
  • If the comparison is part of a larger expression like '(x == None) and y', rewriting may short-circuit differently due to truth value of None vs bool.
  • In eval() or exec() contexts, the rewritten string may fail if the local scope doesn't contain the built-in None after rebinding.
  • If the code relies on the == operator returning a non-boolean (e.g., custom proxy), replacing it with 'is' forces a bool, breaking downstream usage.
