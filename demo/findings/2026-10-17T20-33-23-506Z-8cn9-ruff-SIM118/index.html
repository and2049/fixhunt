Rule analysis

Flags redundant .keys() usage in membership tests like 'x in d.keys()' where direct 'x in d' is preferred.

Fix: Rewrites 'key in obj.keys()' to 'key in obj' by removing the redundant .keys() attribute access while preserving the membership test semantics.

8 hazards
  • If obj is not a dict but has a .keys() method returning a non-container (e.g., generator), removing .keys() may cause TypeError during membership test.
  • If obj.keys() has side effects (e.g., prints, state changes), removing the call eliminates those effects.
  • If obj is a property that returns a dict-like object with .keys(), accessing obj directly may trigger different behavior than obj.keys() due to property logic.
  • If obj is None or lacks __contains__, the rewrite may raise AttributeError instead of returning False.
  • If obj is a custom class where __contains__ differs from membership in .keys() (violating dict contract), semantics change.
  • If the expression uses short-circuiting and obj.keys() is evaluated conditionally, removing .keys() may evaluate obj earlier/later.
  • If obj.keys() is used elsewhere in the same line for another purpose (e.g., assignment), the rewrite breaks that usage.
  • If obj is a built-in type like list (which has no .keys()), the rule shouldn't fire, but if misapplied, the rewrite would fail.
