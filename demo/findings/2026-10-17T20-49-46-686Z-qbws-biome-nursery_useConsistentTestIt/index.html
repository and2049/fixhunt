Rule analysis

The rule flags inconsistent usage of 'it' vs 'test' keywords for test function calls based on configured preferences.

Fix: Replaces 'test' with 'it' or vice versa according to the rule's function and withinDescribe options, preserving all arguments and formatting while respecting syntactic boundaries.

12 hazards
  • Rewriting 'test' in 'const test = value;' would corrupt a variable declaration by changing the identifier, altering runtime value access.
  • Changing 'test' in 'function test() {}' modifies a function declaration's name, breaking recursive calls or external references to that function.
  • Altering 'test' in an import alias like 'import { test as t }' would mismatch the imported binding, causing undefined reference errors.
  • Modifying 'test' inside a comment or string literal would introduce invalid syntax where none existed, potentially creating accidental identifiers.
  • Renaming 'test' in a dynamic property access like 'obj[test]' would change the evaluated key, leading to incorrect property lookup or runtime errors.
  • Rewriting 'test' when followed by JSX (e.g., 'test<div/>') would corrupt the expression by inserting a JSX element where a function call was expected.
  • Changing 'test' in a template literal like `\(test\)` would alter the literal's content, potentially breaking string interpolation or evaluation.
  • Renaming 'test' in a labeled statement ('test: console.log(1)') would change the label name, breaking any 'break test' or 'continue test' references.
  • Modifying 'test' in an import specifier like 'import { test } from "mod"' without updating the import statement would leave the import unchanged, causing a mismatch between the imported binding and its usage.
  • Rewriting 'test' when it's part of a larger identifier like 'testify' would incorrectly truncate or alter the symbol, causing reference errors.
  • Changing 'test' in a type annotation or JSDoc comment (e.g., '@type {test}') would corrupt documentation semantics without affecting runtime, but could break tooling dependencies.
  • Altering 'test' in a destructuring pattern like '{ test } = obj' would rename the binding, causing subsequent uses of 'test' to reference the wrong variable or be undefined.
