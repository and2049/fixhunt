Rule analysis

Flags set() calls wrapping list comprehensions where the elements do not depend on iteration variables.

Fix: Rewrites set([expr for vars in iters if conds]) into {expr for vars in iters if conds}, preserving the comprehension's structure but changing the container from list to set literal.

10 hazards
  • The rewrite may drop inline or block comments attached to the opening bracket, closing bracket, or within the list literal, as Ruff's autofix does not preserve them reliably.
  • If the list comprehension is used elsewhere in the same scope (e.g., assigned to a variable before passing to set()), the refactor breaks that usage by eliminating the list entirely.
  • In rare cases involving ambiguous grammar (e.g., set([...]) * 2), removing brackets could alter precedence and change the expression's meaning.
  • If the comprehension contains a walrus operator (:=) that binds a variable used after the set() call, the refactor may prematurely end the variable's scope or alter its lifetime.
  • When the list comprehension is part of a larger expression (e.g., in a return statement or argument list), the autofix might inadvertently affect formatting or line continuation in ways that break syntax.
  • If the code relies on the list being mutable (e.g., passed to a function that mutates it before set() consumes it), the refactor removes that mutation opportunity, though set() construction already makes this irrelevant—still, any intermediate mutation would be lost.
  • In Python versions prior to 3.6, set literals with comprehensions were not guaranteed to preserve insertion order, but since the original list comprehension also had no order guarantee for set(), this is not a behavioral change—however, if the code mistakenly assumed list order mattered for debugging or side-effect logging, the refactor could obscure intent.
  • If the list comprehension is written across multiple lines with trailing commas or hanging indentation, the autofix may normalize whitespace in a way that conflicts with project style guides (e.g., black vs. Ruff), causing formatting churn.
  • If the set() call is part of a macro-like pattern via eval or exec, the static rewrite could produce invalid code when the string is later executed.
  • If the comprehension includes a conditional expression that raises an exception during evaluation, the refactor does not change evaluation order or short-circuiting, so no semantic hazard arises—but if the list was being inspected for partial results before completion (e.g., in a debugger), that observation capability is lost.
