Rule analysis

Flags for-loops without initialization or increment parts where only a condition remains, suggesting replacement with while loops.

Fix: Replace the for-loop with a while-loop using the condition as the test, keeping the loop body unchanged.

12 hazards
  • Moving variable declarations from the init part to before the loop may cause hoisting issues if the variable is used prior to the loop.
  • If the init part contains side-effecting expressions (e.g., function calls), removing them alters execution order and may omit required initialization.
  • The fix assumes no update part exists; if present but ignored by the rule due to being empty, the rewrite incorrectly drops it.
  • Labels or break/continue statements targeting the for-loop by label may become invalid if the loop structure changes.
  • Comments attached to the for or semicolons may be lost during rewrite if not preserved by the tool.
  • In strict mode, deleting a variable via the init part (if present) would behave differently if the init is removed.
  • If the condition uses `with` or indirect eval, scope resolution could differ between for and while constructs.
  • The rewrite may interfere with automatic semicolon insertion if the loop header is malformed or adjacent to problematic tokens.
  • If the loop is part of a larger expression (e.g., return for (;cond;) expr;), the statement conversion breaks grammar.
  • Using `this` in the condition may capture a different object if the loop rewrite changes execution context indirectly.
  • If the init part declares a variable with `var` that is later accessed outside the loop, moving it outside may not preserve temporal dead zone behavior (though var has none, confusion with let/const could arise).
  • If the condition is a complex expression involving commas, the rewrite may misinterpret precedence or evaluation order.
