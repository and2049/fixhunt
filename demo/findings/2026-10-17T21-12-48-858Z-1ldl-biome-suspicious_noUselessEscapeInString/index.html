Rule analysis

The rule flags unnecessary escape sequences in regular string literals where escaping a character has no semantic effect.

Fix: Remove the backslash before the escaped character, leaving the character itself unchanged in the string literal.

8 hazards
  • In a regex literal like /\a/, removing the backslash changes the pattern to /a/, altering matching behavior.
  • If the escaped character is part of a larger escape sequence like \\n, removing one backslash incorrectly yields \n instead of preserving the intended literal backslash followed by 'n'.
  • In a string used with eval or Function constructor, altering escapes could change the resulting code's syntax or semantics when evaluated.
  • If the string contains a comment-like sequence such as /* or // after fix insertion, it could inadvertently create or break a comment in the source if the string is later interpreted as code.
  • When the string is concatenated with other strings involving line continuations via backslash-newline, removing a backslash could break the line continuation and cause a syntax error.
  • If the escaped character appears in a template literal section that is passed to a tag function, the tag may rely on the raw escape presence for custom processing, so removing it alters the tag's input.
  • In JSX attribute values, although the rule ignores JSX strings, if a similar fix were applied incorrectly, it could change how the attribute value is parsed by the JSX transformer.
  • If the string is used as a key in object property access via bracket notation and the escaped character was relied upon for obfuscation or specific encoding, removing the escape could expose or alter the key unexpectedly.
