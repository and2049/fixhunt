Rule analysis

Flags unnecessary 'noqa' inline comments where none of their listed error codes correspond to actual lint errors present on that line.

Fix: Removes the entire '# noqa: <codes>' comment from the end of the line, preserving any preceding code and whitespace up to but not including the comment.

8 hazards
  • If the line contains only a 'noqa' comment (e.g., '# noqa: F401'), removing it deletes the entire line, potentially altering indentation-sensitive structures like multi-line statement continuations or changing the line count for debugging tools.
  • If the 'noqa' comment is followed by additional text on the same line without a separating '#', that text is incorrectly interpreted as part of the suppression and deleted, which could remove user intent such as explanations or other tool configurations (e.g., turning '# noqa: F401 temporary fix' into just the code prefix).
  • In cases where multiple space-separated tokens follow the 'noqa' comment on the same line (e.g., '# noqa: F401 # some note'), the fix may delete too much or too little depending on how Ruff tokenizes the line, risking partial deletion of adjacent comments or code.
  • If the 'noqa' comment appears inside a string literal (e.g., msg = "ignore this: # noqa: F401"), the rule should not fire, but if it did due to a parsing error, removing it would corrupt the string content and potentially change runtime behavior.
  • When the 'noqa' comment is the only content on a line that serves as a visual separator in a block of code (e.g., between function definitions), removing it may reduce readability but does not affect execution; however, if the line is relied upon by tools that parse source structure (like coverage.py or IDEs), its removal could interfere with those tools.
  • If the line ends with a 'noqa' comment and has trailing whitespace, the fix preserves the whitespace, but in rare cases where whitespace is syntactically significant (e.g., in certain DSLs or when generating code via string concatenation), its preservation might still contribute to unintended behavior—though this is extremely unlikely in standard Python.
  • If the 'noqa' comment suppresses an error that is actually present but masked by a conditional import or platform-specific code (e.g., inside a TYPE_CHECKING block), removing the comment could cause the linter to re-flag the error, but this does not change runtime behavior—only lint output.
  • In files processed by other tools that expect the 'noqa' comment to remain (e.g., for audit trails or compliance), its removal could violate external requirements even though the Python semantics are unchanged.
