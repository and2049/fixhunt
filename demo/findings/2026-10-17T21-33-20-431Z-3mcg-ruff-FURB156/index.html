Rule analysis

Flags hardcoded strings matching known charset literals like digits or ascii letters and suggests replacing them with corresponding `string` module constants.

Fix: Replaces the hardcoded string literal with an attribute access on the `string` module (e.g., `string.digits`, `string.ascii_lowercase`) and adds `import string` at the top of the file if not already present.

8 hazards
  • If the string literal appears inside a function or class scope, adding `import string` at the module level may cause unnecessary imports or circular import issues in rare cases.
  • If the string is used as a default argument value, the rewrite changes the timing of when the `string` module is accessed (at definition time vs call time), potentially affecting behavior if the module is modified later.
  • If the hardcoded string is part of a larger expression (e.g., concatenation or formatting), replacing only the literal may break the expression or produce a syntax error.
  • If the variable name `string` is already in use in the current scope, the import will shadow it, causing `string.digits` to fail with an AttributeError or refer to the wrong object.
  • If the code relies on the specific identity of the string literal (e.g., for interning or `is` comparisons), the rewrite may produce a different string object, breaking identity checks.
  • If the hardcoded string contains escaped characters (like `\t\n\v\f\r `) and is edited manually, the autofix might not recognize it as whitespace, leading to incomplete fixes.
  • If the string is used in a context where its exact byte representation matters (e.g., encoding, cryptography, or binary protocols), replacing it with a `string` constant could alter behavior if the constant differs in encoding or composition.
  • If the code is generated or templated and the string appears in a comment or docstring, the tool might incorrectly modify it, though the rule should avoid non-code contexts—however, flawed parsing could still lead to erroneous changes.
