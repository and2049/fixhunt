Rule analysis

Disallows using logical NOT (`!`) as the top-level condition in an `if-else` statement when both branches exist.

Fix: Removes the logical NOT operator from the condition and swaps the `if` and `else` blocks so the original `else` block becomes the `if` body and vice versa.

8 hazards
  • The condition may contain side effects (e.g., function calls) whose evaluation order or number of executions changes when moved, altering program state.
  • If the condition declares variables via `let` or `const` inside its scope (in some implementations), moving it may break due to TDZ or scope mismatch.
  • The rewritten condition may be harder to read or debug, especially if the original negation was intentional for clarity (e.g., guarding against null/undefined).
  • If the `if` block contains a `break`, `continue`, or `return`, swapping blocks can change control flow in loops or functions.
  • Comments attached to the `!` token or condition may be lost or misplaced during the rewrite, affecting code documentation.
  • In rare cases involving getters with side effects, evaluating the condition twice (if duplicated during transformation) could cause unintended behavior.
  • If the condition is part of a larger expression via operator precedence (though unlikely at top level), removing `!` without proper grouping could misinterpret intent.
  • The fix assumes the condition is a simple boolean expression; if it's a complex expression where `!` is not the outermost operator (but the rule only flags when it is), the logic still holds—but extreme nesting could confuse the transform.

The autofix inverted the condition but failed to add braces around the consequent, producing `if (foo) result += 'B' else result += 'A'` which is a syntax error because an `else` cannot follow a bare statement without braces. This occurs on ordinary code using an `if` without braces and an `else` clause, a perfectly legal and common construct.
