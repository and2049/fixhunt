Rule analysis

Flags invalid `noqa` rule codes in inline comments.

Fix: Removes the entire inline `# noqa: <code>` comment if all codes are invalid; otherwise, removes only the invalid codes from the comment, preserving valid ones and the comment if any valid codes remain.

12 hazards
  • Removing a trailing `# noqa` comment could change the interpretation of preceding tokens if the comment was acting as a line continuation via backslash (though rare in Python).
  • If the `# noqa` comment contains manual spacing or alignment that affects readability or tooling, removing it alters whitespace-sensitive processing.
  • In a line like `x = 1 # noqa: ABC123 # another comment`, removing the invalid code may leave `# # another comment` which is syntactically odd but semantically preserved; however, if the fix improperly handles spacing, it could collapse comments incorrectly.
  • If the line has a `# noqa:` comment with invalid codes and the fix removes the entire comment, any dependent tooling that parses `# noqa` for metadata (even with invalid codes) may lose expected behavior.
  • When the fix removes only part of a `# noqa: code1,code2` comment and leaves a trailing comma (e.g., `# noqa: VALID,`), the resulting comment may be misparsed by tools expecting clean lists.
  • If the line contains a `#` inside a string literal (e.g., `s = "x # noqa: FAKE"`), the rule should not fire, but if it did due to a bug, removing the comment-like text would corrupt the string.
  • If the `# noqa` comment is the only content after code and its removal leaves trailing whitespace, it is semantically neutral but may affect diff tools or formatting expectations.
  • In rare cases where a `# noqa` comment is used to intentionally disable a linter for the next line via some non-standard tool, removing it could re-enable checking incorrectly.
  • If the code line ends with a `# noqa` comment and the fix removes it, and the line previously relied on the comment to avoid trailing whitespace warnings in some editors, removal could reintroduce such warnings (though this is editor-specific, not semantic).
  • When the fix preserves the `# noqa` comment with only valid codes, if the original comment had irregular spacing (e.g., `# noqa: E402`), normalization might alter formatting but not semantics.
  • If the line has multiple `#` comments (e.g., `x = 1 # first # noqa: FAKE`), and the fix removes only the `# noqa` part, the remaining comment structure changes but does not affect execution.
  • If the `# noqa` comment includes a code that is invalid for Ruff but valid for another tool (e.g., `mypy`), and the user relies on Ruff not stripping it due to `lint.external` configuration, the fix would still remove it unless configured otherwise, breaking cross-tool suppression.
