Rule analysis

Flags empty block statements (`{}`) as they serve no purpose unless containing declarations that introduce bindings.

Fix: Removes the empty block statement entirely, preserving surrounding syntax and whitespace except for the braces and their immediate interior.

11 hazards
  • Rewriting `{}` inside a `with` statement changes the object used for property lookup, altering identifier resolution.
  • Removing a block in a comma expression like `( {}, x )` drops the left-hand side, changing the expression's value from `x` to potentially causing a syntax error if the comma was relied upon for sequencing.
  • Deleting a block that follows a label (e.g., `label: {};`) removes the labeled statement, breaking `break label;` or `continue label;` references elsewhere.
  • If the empty block contains a trailing comment (e.g., `{ /* note */ }`), the autofix may discard the comment, losing developer intent.
  • In non-strict mode, a function declaration inside a block is not allowed, but if present due to browser leniency, removing the block could expose it to outer scope, changing hoisting behavior.
  • When the block is the sole member of a `do-while` loop body (e.g., `do {} while (false);`), removing it creates an empty loop body, which is syntactically valid but may affect performance expectations or tooling that counts loop iterations.
  • In a sequence like `if (a) {}; else if (b) {};`, removing the first empty block could merge the `else if` with the prior `if`, changing the binding of the `else` clause if formatting relies on the block to delimit the then-branch.
  • If the empty block is part of a larger expression relying on its presence for automatic semicolon insertion (ASI), such as `return\n{};`, its removal could cause ASI to insert a semicolon after `return`, returning `undefined` instead of the intended value.
  • In a `switch` statement, a case label followed by an empty block (e.g., `case 1: {}; break;`) when rewritten removes the block but leaves the label, which is harmless only if no fall-through is intended; however, if the block was meant to prevent fall-through via explicit emptiness, its removal does not change behavior but may mislead readers about intent.
  • When the block appears immediately after a `yield` expression (e.g., `yield {};`), removing it does not change the yielded value but may affect generator debugging or stack traces that expect a block boundary.
  • In template literals, a tagged template like `tag`{}`` with an empty block afterward (invalid syntax) would not occur, but if malformed code had `{}` adjacent due to a macro, removal could alter parsing; however, this is speculative and not a direct hazard of the rule.

Findings

r2-p008 fix-changes-behaviorlabelled safejudge: real · high ASI Semicolon-Less Hazard

The fix removes a standalone block statement that contains a `let` declaration (`let x = 1`), which creates a new block scope in ES6+. This changes the scope of the variable `x` from being confined to the block to leaking into the enclosing `try` block, altering the program's observable behavior (silent wrong results / scope change). The rule documentation explicitly states blocks with block-level bindings are not redundant, so the fix is incorrect for this construct.
