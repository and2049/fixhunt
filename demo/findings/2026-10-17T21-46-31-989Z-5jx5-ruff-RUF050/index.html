Rule analysis

Flags standalone 'if' statements whose bodies contain only 'pass' or ellipsis ('...').

Fix: Removes the entire 'if' statement if its condition is side-effect-free; otherwise replaces it with the condition as an expression statement.

8 hazards
  • Rewrite drops inline or trailing comments attached to the 'if' line or indented block, altering source documentation.
  • If the condition is a name like 'if x:', the fix treats it as side-effect-free and removes it, but 'x.__bool__()' might have side effects if overridden, changing behavior.
  • When the condition has side effects (e.g., a function call), replacing 'if func(): pass' with 'func()' evaluates the condition once instead of potentially short-circuiting in larger contexts, though here it's standalone so evaluation count remains one—still, if the call was relied upon for truthiness in a now-removed branch, logic may mislead readers.
  • In nested scopes, removing an 'if' block could inadvertently expose variables meant to be conditionally scoped (though Python lacks block scope, this affects readability and potential accidental reuse).
  • If the 'if' statement is the only thing in a module or block, removing it may create an unexpected blank line or affect formatting-dependent tools.
  • The fix may interfere with source‑generation tools that rely on the presence of syntactic scaffolding (like code‑generation templates) even when the body is a no‑op.
  • If the ellipsis '...' is used intentionally as a stub (e.g., in API skeletons), removing the 'if' could delete a meaningful placeholder despite being semantically empty.
  • When the condition involves chained comparisons or complex expressions, extracting it as a standalone statement may hinder debugging (e.g., breakpoint placement on the 'if' line vs. the expression line).
