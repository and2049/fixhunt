Rule analysis

Flags functions lacking an explicit return statement when they contain any return expression.

Fix: Adds an explicit 'return None' statement at the end of the function body, after all existing statements.

8 hazards
  • Adding 'return None' after a try-except-finally block may suppress exceptions raised in the finally clause, as the explicit return will propagate before the finally block completes.
  • If the function contains a yield statement elsewhere, adding 'return None' creates a syntax error because return with a value inside a generator is only allowed in Python 3.3+ and changes the generator's behavior.
  • Inserting 'return None' after a with block may skip execution of context manager's __exit__ method if an exception occurs in the with block and is not handled, altering cleanup semantics.
  • When the function is part of a class hierarchy and overridden in a subclass, adding 'return None' may violate Liskov substitution if the override expects a different return type.
  • If the function is decorated with a decorator that inspects or modifies the return value (e.g., @property, @cached_property), inserting 'return None' may break the decorator's assumptions.
  • In async functions, adding 'return None' after an await expression may alter control flow if the await raises an exception, as the explicit return prevents propagation.
  • If the function's last line is a comment-only line, inserting 'return None' after it may detach trailing comments from the preceding statement, affecting readability or tooling that relies on comment attachment.
  • When the function contains a nested function with a return statement, adding 'return None' in the outer function may cause unintended early termination if control flows through the nested function's definition (which is inert) but the outer function now returns None unconditionally.
